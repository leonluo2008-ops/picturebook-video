# picturebook-video 补充参考

## 22. seedance_mcp 渠道配置与 401 排查（2026-08-24 实测沉淀）

> 单仓 `seedance_mcp/` 的 `.env` 已抽象 3 个渠道变量：`ARK_API_KEY` + `SEEDANCE_BASE_URL`（第三方 Ark 兼容网关，默认回落官方火山）+ `SEEDANCE_MODEL`。**换渠道 = 只改 `.env`，不碰代码**。

### 22.1 wrapper 只 export key → 渠道配置丢失（curl 成功但 MCP 401）

**症状**：更新 `.env` 换第三方渠道 + 重启 gateway 后，MCP `generate_video` 仍 401；但 `curl` 直接 POST 第三方 base URL + 新 key 却**成功**。

**根因**：`~/.hermes/bin/seedance-mcp-wrapper.sh` 早期版本只 `export ARK_API_KEY`，没 export `SEEDANCE_BASE_URL`/`SEEDANCE_MODEL`。MCP server 的 `os.environ.get("SEEDANCE_BASE_URL", 官方)` 落到官方火山端点 + 第三方 key → 401。**curl 成功但 MCP 失败 = 不是 key 问题，是 MCP 进程环境变量缺渠道配置。**

**修复**：wrapper.sh 一次性读 3 变量并全 export：
```bash
CONF=$(python3 -c "
from dotenv import dotenv_values
d = dotenv_values('$SKILL_DIR/.env')
print(d.get('ARK_API_KEY',''))
print(d.get('SEEDANCE_BASE_URL',''))
print(d.get('SEEDANCE_MODEL',''))
")
mapfile -t C <<< "$CONF"
export ARK_API_KEY="${C[0]}"; export SEEDANCE_BASE_URL="${C[1]}"; export SEEDANCE_MODEL="${C[2]}"
```
然后**重启 gateway**（kill watchdog 不会自动重建，gateway 需重启才 spawn MCP）。

**诊断**：`ps aux | grep mcp_server` 找 PID → `tr '\0' '\n' < /proc/<PID>/environ | grep SEEDANCE` 看进程实际加载的渠道。

### 22.2 判断渠道可用性以 `generate_video` 为准

- `verify_api_key` 走 **GET `?page_size=1` list 端点**——第三方网关（如 aigc.learningcat.cn）可能只开 POST 提交端点 → verify_api_key 报 401 / format incorrect 是**假阴性**，不代表生成不可用。
- **业务错误而非 401 = 渠道已通**：对 base URL POST 返回 400 `InvalidParameter`（如 `resolution not valid for model doubao-seedance-2-0-fast`）说明鉴权通过、模型已识别，问题在参数。
- **参数兼容性**：fast 模型经第三方网关可能不认 `resolution` 参数 → 省略 `resolution` 提交即可（仍出 720p）。
- 拿到 `task_id` 才算提交成功；`status: succeeded` + 下载 `video_url` 才算链路走通。

### 22.3 跨电脑安装铁律 — 路径自动探测（禁硬编码用户名 · 2026-08-24）

**症状**：wrapper.sh / INSTALL_TEST.sh 硬编码 `/home/<user>`（本地 `luo` / 云服 `ubuntu` 不同）→ 跨电脑/跨主机安装必挂。旧 INSTALL_TEST.sh 用「固定 5 次 dirname」反推 HERMES_ROOT，只兼容 `profiles/<p>/skills/...` 结构；在根 `~/.hermes/skills/...` 结构下会把 HERMES_ROOT 错判成 `/home`。

**铁律**：wrapper.sh + INSTALL_TEST.sh + smoke_test.py **禁止硬编码用户名/机器**。定位 HERMES_ROOT 用「向上找含 `hermes-agent/` 的目录」，不是数 dirname 次数：

```bash
HERMES_ROOT=""; _D="$(dirname "$(readlink -f "$0")")"
for _i in 1 2 3 4 5 6 7 8; do
  [ -d "$_D/hermes-agent" ] && HERMES_ROOT="$_D" && break
  _D="$(dirname "$_D")"
done
[ -z "$HERMES_ROOT" ] && HERMES_ROOT="$HOME/.hermes"
```

- smoke_test.py：用 `Path(__file__).resolve().parent` 定位 `seedance_mcp/` 和 `.env`，不用绝对路径。
- wrapper 部署位置多候选（`profiles/<p>/bin` 或根 `bin`）都要找。
- **自检**：`bash INSTALL_TEST.sh 2>&1 | head -4` 的 `HERMES_ROOT=` 应为真实 `.hermes` 绝对路径；`grep -c "/home/luo\|/home/ubuntu" <wrapper>` 应为 0。
- INSTALL_TEST.sh 端到端 Step 7 的 wait_and_download 段也必须传 `SEEDANCE_BASE_URL`/`SEEDANCE_MODEL` 环境变量（只传 key → 查不到第三方 task → 假失败）。
- 完整跨电脑安装 3 铁律见 picturebook-video 仓 `references/seedance-mcp-install-ironrules.md`。

### 22.4 生图/改图任务在第三方网关的探测定论（2026-09-01 工程师 5.jpg「图纸→腋下纸筒」改图实测）

**定论**：aigc.learningcat.cn 只白名单代理 Seedance 视频 tasks 链路，**未部署任何图片生成模型**——seedream/seededit 改图经此网关走不通，应回执 peer 换官方 Ark key 或其他生图渠道，勿在网关上反复换模型名硬试。

实测证据链（~2 分钟可复跑）：
1. Ark 风格图片路径全 404：`/api/v3/images/generations`、`/ark/v3/images/generations`、`/ark/api/v3/images/generations`、`/v3/images/generations`、`/api/v1/...` 等 12+ 候选全 `404 page not found`。
2. OpenAI 风格 `/v1/images/generations` 路径**存在**（dummy key→401），但真 key 下所有 seedream/seededit 模型名（-4-0-250828 / -4-0 / -4.0 / seededit-3.0-i2i / -3-0-t2i / jimeng…）全 404 `DeploymentNotFound` = 路径在白名单、模型没部署。
3. 视频 tasks 路径 + seedream 模型名 → `the specified model doubao-seedream-4-0 does not support content generation` = 网关认识模型名但该路径族只出视频任务。
4. `GET /v1/models` 404（无法列模型）→ 只能按「① 路径探测(dummy key) → ② 真 key 试模型名」顺序排查。

**探测成本陷阱**：对「提交即建任务」型端点（如 contents/generations/tasks）做连通性探测时，**真 key + 真模型名 + 可执行 content = 真提交真计费**（实测一次控制探针误建 cgt-* 视频任务入队）。路径存在性探测一律用 dummy key（401/404 即定论）；真 key 只留给「业务错误=渠道已通」（§22.2）验证步，且 body 用必缺参数的最小占位（期待 InvalidParameter），不给完整可执行 content。

**跨会话续做识别**：peer 问「继续刚才的 X 任务了吗/汇报进度」→ 先 `session_search`（主题词 newest）定位上一会话，直接读其脚本与日志落点（如 /tmp/seedream_edit.sh、/tmp/seedream_run1.log）判断它是「跑完失败」还是「中途被杀」——上一会话已把 model 阶梯跑完并留结构化日志时，续做 = 读日志接结论，不重跑已证死的分支。

**key 遮蔽与归属判定（A2A 涉 key 任务纪律 · 2026-09-01 补充实测）**：
- **遮蔽**：环境检查只回显可公开项——变量名清单（`grep -oE '^(export[[:space:]]+)?[A-Za-z_]+' .env | awk '{print $NF}' | sort -u`）+ `${VAR:+SET(len=${#VAR},value=****)}`；BASE_URL / MODEL 可回显值，key 一律 `****`。key 只经 `source .env` + 环境变量进 curl，不落盘、不回显、不进任何日志/响应体输出；uguu 响应里的 `token` 字段也要 sed 遮蔽。
- **key 归属一步判定**：拿网关 key POST 官方 `ark.cn-beijing.volces.com/api/v3/images/generations`（空体）→ 401 `"The API key format is incorrect"` = 网关自发 key，官方端点绕行不可行，只能等网关开通部署或回执 peer 换渠道（与 §22.2 verify_api_key 假阴性区分：这是官方端点对 key 格式的确定性拒绝）。
- **MODEL 变量实名陷阱**：`.env` 里实名 `SEEDANCE_MODEL`，值是**视频**模型（如 `doubao-seedance-2-0-fast-260128`）；peer 指令笼统说「MODEL 变量」时，勿把视频模型名填进 images/generations 请求。
- uguu 图片上传与视频同款：multipart 字段 `files[]`，HTTP 200 + `success:true` + `files[0].url`。

## 1. 认知页 vs 封面判定（2026-08-02 温暖实测）

### 问题
1.jpg（太阳+WARM/温暖文字）被误标为"弃用(封面)"，实际是段#1「温暖，WARM！」的配图。用户纠正："第一个视频差认知页的画面"。

### 判定标准

| 类型 | 特征 | 处理 |
|------|------|------|
| **认知页** | 有标题文字 + 有旁白对应的主体内容（太阳/树/动物/场景等） | 保留，配段#1 |
| **封面** | 只有纯标题文字/装饰，无旁白对应的主体内容 | 弃用 |

### 判定流程

```
vision_analyze 拿到图的主体描述
    ↓
图中有无旁白段#1对应的主体内容？
    ├─ 有 → 认知页，保留，配段#1
    └─ 无（只有标题文字/装饰）→ 封面，弃用
```

### 用户反馈信号

| 用户原话 | 含义 | 处理 |
|----------|------|------|
| "第一个视频差认知页的画面" | 1.jpg被误标为封面弃用，实际是段#1配图 | 保留1.jpg配段#1 |
| "第X个视频中XX的画面中手有问题" | 参考图手部渲染异常 | 用户提供新图后替换并重生成 |
| "重新给你XX的场景图片，重新生成第X个视频" | 用户提供新图替换 | 覆盖原文件，更新prompt，重提交 |

### 常见案例

| 图内容 | 判定 | 原因 |
|--------|------|------|
| 太阳+WARM/温暖文字 | ✅ 认知页 | 太阳是段#1「温暖，WARM！」的主体 |
| 大树+TREE/树文字 | ✅ 认知页 | 树是段#1「树，TREE！」的主体 |
| 只有标题文字+纯色背景 | ❌ 封面 | 无旁白对应的主体内容 |
| 只有标题文字+装饰性图案 | ❌ 封面 | 装饰图案不是旁白主体 |

### 反模式

- ❌ 看到1.jpg有标题文字就自动标"弃用(封面)"
- ❌ 默认认为素材包一定有封面弃用图（8图=8段1:1时可能无封面）
- ✅ 先看vision描述中是否有旁白段#1对应的主体，有则保留

## 8. Seedance 敏感内容误判处理（2026-08-02 太阳实测）

### 场景
太阳绘本 Clip 2（段#5-#8，图5-8.jpg）提交两次均被 Seedance 拦截：
```
OutputVideoSensitiveContentDetected: The request failed because the output video may contain sensitive information.
```

### 根因
8.jpg（小女孩背影挥手向太阳告别）被 Seedance 敏感检测误判。图片内容完全无害（儿童教育插图），属于自动化审核误报。

### 处理流程

```
任务失败（OutputVideoSensitiveContentDetected）
    ↓
Step 1: 拆Clip为更小的子Clip（≤2张图/子Clip）
    ↓
Step 2: 分别提交子Clip
    ├─ 不含问题图的子Clip → 通常直接通过
    └─ 含问题图的子Clip → 单独提交，如果仍失败则：
        ├─ 尝试去掉问题图，只用其他图
        └─ 或告知用户该图无法通过审核
    ↓
Step 3: 全部通过后，用户自行在剪映合并
```

### 实测结果

| 子Clip | 图 | 结果 |
|--------|-----|------|
| Clip 2a（7s） | 5.jpg+6.jpg（花朵场景） | ✅ 通过 |
| Clip 2b（7s） | 7.jpg+8.jpg（落山+挥手） | ✅ 通过 |

### 注意事项

- 拆Clip后总时长会略增（13s → 7s+7s=14s），差额为取整余量
- 不需要重新走Step 1-4，直接从Step 5改prompt+提交
- 拆Clip后prompt要精简（去掉被拆走的段）
- 如果拆后仍失败，尝试去掉问题图单独提交

## 2. 用户换图重做流程（2026-08-02 温暖实测）

### 场景
用户对已生成的视频中某张参考图不满意（如手部问题），提供新图要求重新生成对应Clip。

### 流程

```
用户说"重新给你XX的场景图片，重新生成第X个视频"
    ↓
Step 1: 用新图替换旧文件（cp 覆盖原文件名）
    ↓
Step 2: vision_analyze 新图，确认主体/姿态/文字元素
    ↓
Step 3: 更新对应Clip的prompt（段1视觉基底 + 段2动作描述，去掉已移除的元素）
    ↓
Step 4: 重新提交seedance（同duration/ratio/ref_images）
    ↓
Step 5: wait_and_download → 发飞书
```

### 注意事项

- 只重新生成被替换的Clip，其他Clip不动
- 文件名保持原样（覆盖原文件），不新建文件
- prompt中移除已去掉的元素（如手），调整动作描述
- 不需要重新走Step 1-4全流程，直接从Step 5开始

## 5. Vision 幻觉级联陷阱（2026-08-03 Snow 绘本实测）

### 问题
第一次 vision_analyze 全部 8 张图后，2.jpg 被幻觉描述为"雪地+两个树桩+灌木"——**实际 2.jpg 是纸雪花散落图**。这个错误级联到后续所有图的描述，导致每张图的内容描述整体偏移 1 位，最终生成的视频图片缺失/错位。

### 根因
- vision 模型对拼贴/手工风格（纸雪花 vs 雪地）的区分能力不足
- agent 没有交叉验证，直接信任了第一次输出
- Step 2 的图-段对位表只检查"图 vs 段"的对应关系，**不检查"vision 描述 vs 图实际内容"的准确性**

### 预防措施

#### 5.1 交叉验证法（写 prompt 前必做）

写段 1 视觉基底前，对每张图做二次验证：

```
# 第一次 vision_analyze（全部 N 张）
vision_analyze("1.jpg") → 描述 A
vision_analyze("2.jpg") → 描述 B
...

# 写段 1 时，对关键图做二次确认
vision_analyze("2.jpg", question="确认：这张图是雪地场景还是纸雪花散落？")
```

#### 5.2 文件名-内容一致性检查

如果 vision 描述跟文件名/序号预期严重不符，标记为可疑：

| 文件名 | 预期（从 SRT 推断） | vision 描述 | 状态 |
|--------|-------------------|-------------|------|
| 2.jpg | 白白的雪（纸雪花） | 雪地+树桩 | ❌ 可疑 |
| 3.jpg | 地面上的雪（雪地） | 松枝+厚雪 | ❌ 可疑 |

#### 5.3 段 1 写完后自检

写完段 1（视觉基底）后，**逐图对照**：
- 段 1 对 @Image2 的描述是否跟 vision 看到的 2.jpg 一致？
- 如果描述跟 vision 输出矛盾，重新 vision_analyze 该图

#### 5.4 用户反馈后的修复流程

当用户反馈"图片缺失/错位"时：
1. **不要直接重写 prompt**——先重新 vision_analyze 全部图，确认每张图的实际内容
2. 输出修正后的图-内容对照表给用户确认
3. 确认无误后再重写 prompt 和重新提交

### 反模式

| 反模式 | 后果 |
|--------|------|
| ❌ 第一次 vision 输出后直接写 prompt，不交叉验证 | 幻觉级联，整条线偏移 |
| ❌ 发现描述可疑但不重新 vision_analyze | 带着错误继续 |
| ❌ 用户反馈后只改 prompt 不重新看图 | 改的只是文字，图还是错的 |
| ✅ 写段 1 前对每张图做二次确认 | 确保描述准确 |

## 6. R11 空间目标关键词匹配陷阱（2026-08-03 Snow 绘本实测）

### 问题
verify_prompt.py 的 R11 检查使用精确关键词匹配（`space_keywords` 列表），自然语言描述中的"从画面四周向中央"没有命中"画面中央"这个关键词，导致 FAIL。

### 根因
verify_prompt.py 的 `space_keywords` 列表是固定白名单（见 `scripts/verify_prompt.py` 第 448-463 行），包含"画面中央"但不包含"向中央"、"从四周"等变体。

### 修复方法
在镜头段描述中**显式使用白名单中的关键词**，而不是依赖自然语言变体：

| 想表达的意思 | 必须用的关键词 | 示例 |
|-------------|---------------|------|
| 镜头穿过画面中心 | `穿过画面中央` | "镜头缓慢推近到松枝特写，穿过画面中央" |
| 从左侧横移 | `从左侧` | "镜头从左侧向右横移扫过雪地" |

## 11. verify_prompt.py R7/R8 段号格式陷阱 — `段#N` 不匹配 regex（2026-08-04 Garbage Truck 实测）

### 问题

写段 2 镜头绑定和段 3 关键节点对照时，用 `段#1旁白` 和 `段#1念\"...\"`（带 `#` 号）—— verify_prompt.py 的 R7 和 R8 正则 `段\\s*\\d+` **不匹配 `#` 号**，全部 FAIL。

### 根因

verify_prompt.py 的 regex 是 `段\\s*\\d+`，只匹配 `段1` / `段 1`，不匹配 `段#1` / `段 #1`。

### 修复

| 写法 | R7 结果 | R8 结果 |
|------|---------|---------|
| `镜头1（@Image1 + 段#1旁白）：` | ❌ FAIL | — |
| `镜头1（@Image1 + 段1旁白）：` | ✅ ok | — |
| `段#1念\"垃圾车 GARBAGE TRUCK！\"：` | — | ❌ FAIL |
| `段1念\"垃圾车 GARBAGE TRUCK！\"：` | — | ✅ ok |

### 自检方法

写 prompt 时统一用 `段N`（无 `#`），不要混用 `段#N`。跑 verify_prompt.py 前先 `grep '段#'` 检查是否有残留的 `#` 号。

### 反模式

- ❌ 按习惯写 `段#1`（带 `#` 号）
- ❌ 混用 `段1` 和 `段#1`（部分通过部分 FAIL）
- ✅ 全程统一用 `段N` 格式

## 12. 横版图片竖版输出处理（2026-08-04 Garbage Truck 实测 · **2026-09-01 农民批两轮推翻更新 · 见 §12b 源头竖版流程**）

> ⚠️ **v3 更新（2026-09-01 晚）**：本节 B2 预合成画布方案（PIL 横条居中 + 模糊延展带）已被用户**正式否决**——「不能用这种方式，这种方式和横版就没有什么区别」。用户拍板的根治方案 = **§12b 源头竖版流程**（反推提示词→即梦重出真 9:16 参考图）。本节保留仅作实验记录与 §12b 的对照基线。

### 场景

用户给的图片是横版（1920x1200 = 1.6:1），但要求输出竖版 9:16 视频。

### ⚠️ 根因（2026-09-01 官方文档实锤 + 农民批实测）

Seedance 官方文档「图片裁剪规则」：**ratio 与上传图片宽高比不一致时，方舟会对参考图居中裁剪**。1920×1200 喂 9:16 → 实际只保留中间 ~675px 竖带，**带外像素模型根本看不见**。

**农民批实测后果**：clip4 拖拉机车头被裁、clip6 木推车消失且标牌被改画、clip1 首帧 FARMER 左侧 F 出画。横版直接喂原图不是「自动构图」，是**真裁剪**。

### 三方案对照实验（2026-09-01 clip6 苹果园图 A/B/B2 实测）

| 方案 | 做法 | 实测结果 |
|------|------|---------|
| ❌ A·提示词层 | 横版原图 + 强指令「完整内容全部保留进竖版禁裁任何元素」 | 木推车**仍然消失**——被裁掉的像素提示词救不回，只能脑补 |
| ✅ B/B2·素材层预合成 9:16 画布 | PIL：全图等比缩放至 1080 宽（得 1080×675 中带）居中放入 1080×1920 画布，上下延展带用「取图缘 60px → 缩到 1/12 再放大 + GaussianBlur(18)」做柔化延展 | **木推车完整回归**、标牌完整、无黑边；B2 模糊带自然可接受 |
| ❌ 手动裁剪 | PIL 直接裁成 9:16 | 用户最反感（毁主体，铁律） |

### 分流决策规则（现行标准）

1. **边缘有重要元素**（车辆/推车/标牌/文字贴近左右边缘）→ **必走 B2 预合成 9:16 画布**（延展带模糊柔化，prompt 注明「上方/下方为模糊柔和的延伸带」）
2. **边缘纯背景**（主体居中，两侧只是天空/草地/麦田延续）→ 可直接喂横版原图 + ratio=9:16（火锅流程旧路径仍可用，但要知道边缘会被裁）
3. **Step 2 vision 自检新增第 7 项**：逐图判断「左右边缘 15% 区域内是否有独立元素」→ 有 = 标记需预合成
4. **更优根治**：生图阶段直接出 9:16 竖版图（源头解决，无需转换）

### 代码模板（B2 柔化延展带）

```python
from PIL import Image, ImageFilter
im = Image.open(src)  # 1920x1200
cw, ch = 1080, 1920
strip = im.resize((cw, round(im.height*cw/im.width)))  # 1080x675
y0 = (ch - strip.height)//2
canvas = Image.new('RGB', (cw, ch))
top = im.crop((0,0,1920,60)).resize((cw//12, y0//12)).resize((cw, y0)).filter(ImageFilter.GaussianBlur(18))
bot = im.crop((0,im.height-60,1920,im.height)).resize((cw//12, (ch-y0-strip.height)//12)).resize((cw, ch-y0-strip.height)).filter(ImageFilter.GaussianBlur(18))
canvas.paste(top,(0,0)); canvas.paste(strip,(0,y0)); canvas.paste(bot,(0,y0+strip.height))
```

### 权衡提示

预合成画布 = 中带内容只占画面 35% 高度 + 65% 模糊延展带。用户偏好「填满不留白」时，延展带观感需验收；若不能接受，回到方案 3（生图出 9:16）或与用户确认接受边缘裁切。

### 反模式

- ❌ 给横版图片上下加黑边补成竖版再提交（用户拒绝过）
- ❌ 用 PIL 裁剪图片到 9:16（毁主体）
- ❌ 相信「直接喂横版原图 = seedance 自动完整构图」——边缘元素会被真裁掉（2026-09-01 推翻）
- ❌ 试图用提示词「救回」被裁掉的元素（A 实验证伪）
- ❌ **预合成画布（B2：横条居中 + 模糊延展带）—— 2026-09-01 晚被用户否决：「这种方式和横版就没有什么区别」**（竖版空间没被利用，画面本质仍是横构图塞进竖框）→ 正解是 §12b 源头竖版重出图
- ✅ **源头竖版（§12b 用户拍板根治路径）**：反推参考图提示词 → 即梦重出真 9:16 竖版图 → 视频管线直接喂竖版图
- ✅ 仅当用户明确接受「横构图 + 空边」观感时才允许直接喂横版原图（边缘纯背景类低风险页）

## 12b. 源头竖版流程：横版参考图 → 反推提示词 → 即梦重出 9:16 竖版图（2026-09-01 农民批用户拍板 · 现行标准）

> **用户原话**：「在你的skill里，有一个制作静态绘本的skill，其实你看到的所有参考图都是它生成的。我觉得你可以整合那个skill里的提示词编写的部分内容：①反推参考图提示词 ②按照之前的结构输出竖版的生图提示词 ③用户拿到提示词去即梦批量生成竖版参考图。只是宽高比、图片的比例发生了变化，但是图片的内容不要发生变化。这个方式你看是否可行？」→ 实测验证可行，后续横转竖一律走本流程。

### 三步流程（每步产出物与验收点）

1. **反推参考图提示词（vision 全要素提取）**
   - 逐张 vision_analyze 提取 8 类要素：完整外观（帽/衫/裤/鞋/表情/五官质感）/ 动作姿态（哪只手做什么+道具细节）/ 场景元素（树/车/动物数量颜色）/ 标牌（边框颜色/文字颜色字体位置）/ 背景与地面 / 画风笔触 / 所有文字精确内容与颜色
   - 提炼**统一外观锚点**一句话（本例：「金黄草编宽檐帽+红黑格子长袖衫袖口卷起+棕色背带工装裤银扣+棕胶靴+粉腮红黑葡萄眼」）+ **画风锚点**（蜡笔手绘童趣风）→ 写进【全局设计约定】
   - 标牌样式**逐图保留原图差异**（彩虹边/绿边/棕描边等，不要统一抹平）
2. **改竖版构图 → 输出 9:16 生图提示词（picturebook-creator L4 四字段规范）**
   - 内容与原横版**逐元素一致**，只改构图：天空元素向上延伸、地面草地向下延伸填满竖版；标牌移上部居中；前景元素（菜畦/小动物/推车）压下带；主体严格居中远离左右边缘
   - 保留 L4 引导语（防文字污染 ⚠️ + 一致性 + 居中裁剪预留）+ 【全局设计约定】+【主要场景锚点】+ 每页四字段（旁白/比例/页面类型/生图提示词）
   - P1 认知页：字母块横贯一行放中下部（竖版里一行大字母正好，不竖排变形）
   - **⚠️ 字符数硬约束：< 2000 字符**（用户实测要求——原 1.2 万字完整版被拒，精简压缩后 1489 字通过。压缩法：引导语 3 行、约定用「|」分隔、提示词压成一句式保留全部要素）
3. **用户拿提示词去即梦批量生成竖版图 → 回传 → 视频管线**
   - SRT/clip 划分现成可复用；只换图 + 重写 prompt（竖版图构图已在生图阶段定型，seedance prompt 从「构图适配」简化为「动作执行」）→ Step 5 → Step 6 重摇 → concat

### ⚠️ 反推时必核：图↔旁白一致性 + 8 页场景唯一性（2026-09-01 农民批实测教训）

- **原始横版素材本身可能内藏重复**：农民批 2.jpg 与 4.jpg 都是「农民坐拖拉机」（旁白却不同：来了 vs 开着拖拉机）——即梦生成横版时埋的雷。反推提示词**照抄放大**了这个重复，被用户当场打回：「你写的提示词里面有重复的图片啊，这怎么行呢？你至少要保证那个参考图和旁白要基本一致呀，第二张和第四张图是重复的，完全是一样的」
- **铁律**：反推完成后必须逐页核对「图↔旁白基本一致 + 8 页场景互不重复」；发现重复页 = 重新设计该页场景（本例 P2「来了」→ 改为扛锄头沿田间土路走来挥手，与 P4 驾驶拖拉机区分开）
- 判定细则：两页同道具（如都含铁锨）不算重复——**主体动作 + 场景语义**都同才算；「来了」类出场页优先换成行走/挥手等登场感画面
- 视频管线侧对应：旧素材 2/4 图重复的 clip 成片也会两个画面雷同（用户看视频时会发现「画面跟旁白对不上」），源头竖版重出图时一并修复

### 输出交付物

- `<工作区>/<主题>/竖版生图提示词.md`（或 `_精简版`）——用户直接复制整段去即梦批量生成
- 单页提示词可被用户单独索取（「你把P2的生图提示词给我」）——从文件逐块提取，**附提醒：单发一句需配全局约定一起用，否则角色外观漂移**

### 与 §12 的关系

- §12 的 B2 预合成画布 = **已否决的中间方案**（保留作实验记录）；§12b = 现行标准
- 若用户急需出片且来不及重出图：唯一可接受的临时路径 = 接受边缘裁切风险直接喂横版原图（仅边缘纯背景页）+ 主动告知风险

## 12c. Step 1.5 角色一致性协议 + 人物反丑化（2026-09-02 消防员批实测 · 用户两次反馈沉淀）

### 12c.1 跨图风格/角色不一致（用户原话「我生成图片中画面风格和人物角色没有保持一致」）

**根因**：即梦每次生成互相独立、**无跨图记忆**。风格/角色锚点只写在文件顶部「全局约定」块里、用户生成第 2-8 张时单独贴场景句 = 模型根本看不到锚点 → 各画各的。

**修复（提示词文件 v2 结构）**：
1. **每条提示词自含四锚点**：`风格锚点` + `角色锚点`（外观逐项：发型/眼睛/腮红/头盔/服装/鞋/头身比）+ `场景`（9:16 构图带位）+ `文字锚点`（两行文字+严禁清单）——四段措辞**逐字相同**，单贴任何一条都带全套设定；每条仍 ≤2000 字符
2. **生成方法（比提示词更硬的保险）**：先只生成第 1 张挑最佳成品 → 即梦上传该成品作「参考图/智能参考（角色一致性）」跑余下 N-1 张；同一模型版本一次跑完，中途不换模型
3. 配角（仅某页出现）在那一页的角色锚点尾部单独补一句

### 12c.2 眼睛反丑化 v3 配方（用户原话「所有图中角色的眼睛太丑了，请你重新修改」；8/8 验证通过）

- ❌ 空泛形容词（"好看的/水灵的大眼睛"）= 给模型自由发挥空间 → 纯棕实心圆点豆豆眼
- ✅ 具体画法结构：`大而圆的深棕色水润眼睛——瞳孔左上有一大一小两个白色圆形高光点，瞳孔底部浅棕色渐变透光，上眼睑一条深棕色细睫毛线，眼神明亮有神`
- ✅ 严禁清单紧跟其后：`严禁纯黑实心圆点眼、无高光死鱼眼、呆滞空洞眼神；严禁双眼不对称、斗鸡眼、斜视；严禁夸张巨大眼睛`
- 配角加一句"同款水润大眼睛"；用户看图给视觉反馈后 = 重写全部页的对应锚点字段（同 caterpillar 反丑化重写模式，不能只改一张）

**本批端到端结果**：v2 一致性 + v3 眼睛修复后，8/8 竖版图验收全过，3 clips 一次提交零返工。

## 14. 只改指定画面不动其他（2026-08-04 九/五/一 三本实测）

### 问题

用户要求修改第2画面（小鸭数量），agent 同时修改了第3画面（胡萝卜数量），用户打回"你把第3个画面改的不正确了"。

### 根因

Agent 在修改 prompt 时，为了"一致性"或"顺手"修改了其他画面，但用户只要求改指定画面。

### 修复方案

```markdown
❌ 错误：用户说"改第2画面" → 同时改了第1、2、3画面
✅ 正确：用户说"改第2画面" → 只改第2画面，其他保持原样
```

### 操作流程

1. 用 `read_file` 读取当前 prompt
2. 只修改用户指定的镜头段
3. 其他镜头段**一个字不动**
4. 提交前检查：是否只改了指定画面？

### 反模式

- ❌ 为了"一致性"顺手改其他画面
- ❌ 为了"让 prompt 更完整"加内容到其他镜头
- ❌ 修改排列描述时连带改了其他画面的排列方式
- ✅ 只改用户指定的画面，其他保持原样

## 15. 计数类绘本数量控制迭代策略（2026-08-04 九/五/八 三本实测）

### 问题

Seedance 对画面中物体精确数量控制不稳定，计数类绘本（数字书）经常出现数量不对。

### 迭代策略

| 轮次 | 修复 | 说明 |
|------|------|------|
| 1 | 精确化排列描述 | 从"排成两行"→"后排5只、前排4只交错排列" |
| 2 | 切换运镜模式 | 从"特写→拉远"→"全景→推近→拉远" |
| 3 | 拆独立短 Clip | 4-6s，只用 1 张参考图，单独提交 |

### 用户反馈模式

| 用户原话 | 含义 | 处理 |
|----------|------|------|
| "第2画面修改运镜，要能显示出9只鸭子" | 拉远不够 | 先精确排列，再切换运镜 |
| "第2画面的鸭子数量还是不对，请继续修改" | 前两轮失败 | 拆独立短 Clip |
| "你把第3个画面改的不正确了" | 误改其他画面 | 只改指定画面 |

### 问题

Seedance generate_audio 有时会念错旁白内容。例如：
- 旁白原文：`"红色的单轨列车，monorail"`
- Seedance 念成：`"红色单轨的货车"`

### 根因

Seedance 内置 TTS 对中文长句的语义理解不稳定，特别是当句子包含颜色+物体+英文混合时容易混淆。

### 修复方法

在段 5 音频描述的人声旁白行后加括号注释，显式纠正：

```markdown
段5 · 音频描述：
人声旁白："红色的单轨列车，monorail"（注意：旁白是"红色的单轨列车，monorail"，不是货车，是单轨列车）
音效：列车行驶声
人声旁白："单轨列车开得好快，monorail"（注意：旁白是"单轨列车开得好快，monorail"）
音效：列车快速行驶声，风声呼啸
```

### 原理

Seedance 的 TTS 模型会读取括号内的纠正说明作为额外上下文，提高旁白准确率。

### 如果一次修复不成功

- 加强注释措辞（更明确地指出错误内容）
- 重新提交同一 prompt（seedance 每次生成有随机性）
- 如果多次失败，考虑用 MiniMax TTS 独立生成旁白（见 seedance-prompt-pitfalls 陷阱 #2）

### 反模式

- ❌ 只改 prompt 段 1-4 不改段 5 音频描述
- ❌ 重新提交完全相同的 prompt（不解决问题）
- ✅ 在段 5 加括号纠正注释后重新提交

### 问题

写段 2 镜头绑定和段 3 关键节点对照时，用 `段#1旁白` 和 `段#1念"..."`（带 `#` 号）—— verify_prompt.py 的 R7 和 R8 正则 `段\s*\d+` **不匹配 `#` 号**，全部 FAIL。

### 根因

verify_prompt.py 的 regex 是 `段\s*\d+`，只匹配 `段1` / `段 1`，不匹配 `段#1` / `段 #1`。

### 修复

| 写法 | R7 结果 | R8 结果 |
|------|---------|---------|
| `镜头1（@Image1 + 段#1旁白）：` | ❌ FAIL | — |
| `镜头1（@Image1 + 段1旁白）：` | ✅ ok | — |
| `段#1念"垃圾车 GARBAGE TRUCK！"：` | — | ❌ FAIL |
| `段1念"垃圾车 GARBAGE TRUCK！"：` | — | ✅ ok |

### 自检方法

写 prompt 时统一用 `段N`（无 `#`），不要混用 `段#N`。跑 verify_prompt.py 前先 `grep '段#'` 检查是否有残留的 `#` 号。

### 反模式

- ❌ 按习惯写 `段#1`（带 `#` 号）
- ❌ 混用 `段1` 和 `段#1`（部分通过部分 FAIL）
- ✅ 全程统一用 `段N` 格式

## 16. 核心词文字约束 — 段1和末尾只引用核心词对（2026-08-06 鱿鱼实测）

## 17. 音频-SRT 逐字对齐规则（2026-08-06 推土机实测）

### 问题

用户反馈：**"第2视频的第一个画面音频有误"** + **"画面3音频有误"**

### 根因

段 5 音频描述中的 `人声旁白：「{SRT原文}」` 与 SRT 文件不一致——漏了英文部分、或缩写/改写了中文部分。用户逐句核对音频文本与 SRT 原文。

### 规则

段 5 音频描述中的 `人声旁白：「{SRT原文}」` 必须与 SRT 文件**逐字逐标点一致**。

| 正确 | 错误 |
|------|------|
| `人声旁白：「推土机有履带，bulldozer」` | `人声旁白：「推土机有履带」`（漏了英文） |
| `人声旁白：「推土机在工地上，bulldozer！」` | `人声旁白：「推土机在工地上」`（漏了英文和感叹号） |
| `人声旁白：「推土机后面有松土耙，bulldozer」` | `人声旁白：「推土机后面有松土耙」`（漏了英文） |

### 检查方法

写完段 5 后，逐段对照 SRT 原文，确保：
1. 中文部分完全一致（包括标点：逗号、感叹号、问号）
2. 英文部分完全一致（包括大小写、标点）
3. 中英文之间的分隔符一致（逗号/空格）

### 反模式

- 只写中文部分，省略英文核心词
- 改写中文部分（如"推土机有履带"→"有履带"）
- 省略标点（如去掉感叹号）
- 逐字逐标点复制 SRT 原文

## 18. 动作触发词完整短语规则（2026-08-06 推土机实测）

### 问题

用户反馈：**"第3个视频第二个画面中文核心词错误"**

### 根因

段 2 和段 3 中的动作触发词使用了缩写（如"有履带"）而非 SRT 中文部分的完整短语（"推土机有履带"）。用户检查触发词是否与 SRT 中文部分完整匹配。

### 规则

段 2 和段 3 中的动作触发词必须使用 SRT 中文部分的**完整短语**（主语+谓语），不能只截取关键词。

| SRT 原文 | 正确触发词 | 错误触发词 |
|----------|--------------|--------------|
| `推土机有履带，bulldozer` | `念到「推土机有履带」时` | `念到「有履带」时` |
| `推土机在工地上，bulldozer！` | `念到「推土机在工地上」时` | `念到「在工地上」时` |
| `推土机后面有松土耙，bulldozer` | `念到「推土机后面有松土耙」时` | `念到「松土耙」时` |
| `旗鱼的嘴巴尖尖长长，sailfish` | `念到「旗鱼的嘴巴尖尖长长」时` | `念到「尖尖长长」时` |

### 原因

seedance 需要完整旁白文本才能精确对齐时间点，截取关键词会导致动作与旁白不同步。

### 反模式

- 段 2 写 `念到「有履带」时履带转动速度加快`（截取关键词）

- 段 2 写 `念到「推土机有履带」时履带转动速度加快`（完整短语）
- 段 3 写 `段 3 念"推土机有履带，bulldozer"：履带转动对应"推土机有履带"`（完整短语）

## 19. 旁白语义驱动的持续动作规则（2026-08-06 高铁实测 · 2026-08-06 高铁二次修正）

### 问题

用户反馈：「第2个视频画面一的旁白是高铁跑得飞快，画面没有体现出跑的飞快」

### 根因

段 2 镜头 1 的动作描述只写了触发式动作（念到「bullet train」时速度线喷射变密集），但旁白「高铁跑得飞快」的语义是**从开头就持续高速**，不是只在末尾触发一次。seedance 默认从静止开始，只在触发点动一下，不符合「跑得飞快」的持续语义。

### 规则

当旁白包含**持续状态/持续动作**的语义（跑得飞快、游得飞快、一直转、不停摆动等）时，段 2 镜头描述必须：

1. **从镜头开始就持续动作**：速度线持续喷射、车身持续快速摆动、车轮持续快速转动
2. **整体呈现持续状态**：用「整体呈现高速行驶状态」等描述锁定基调
3. **触发词用于强调峰值**：念到对应词时动作达到峰值（最密集/最大幅度），而不是从无到有

### 速度类旁白的两种表现手法

| 手法 | 描述 | 适用场景 | 用户反馈 |
|------|------|----------|----------|
| **振动法**（第一轮修复） | 速度线持续喷射 + 主体持续快速前后摆动 | 动物/生物（鱿鱼/海马/旗鱼） | 用户说「画面没有体现出跑的飞快」 |
| **滑动法**（第二轮修复 · 2026-08-06 新增） | 主体从画面一侧向另一侧快速滑动穿过画面（如从右向左） | 车辆/列车（高铁/火车/汽车） | 用户说「换成让高铁往前面跑起来的镜头」 |

**关键区别**：车辆类主体（有轮子/在轨道上）用**滑动法**（水平位移）比振动法（原地摆动）更能体现速度感。生物类主体（无轮子/在水中）用振动法更自然。

### 滑动法写法模板

```
镜头 1（主体 @ImageN + 段 N 旁白「旁白原文，keyword！」）：
中景固定镜头。主体在画面右侧，车身从画面右侧向画面左侧方向快速滑动穿过画面
（像在铁轨上向前飞驰），车尾彩色速度线持续向后喷射，车轮快速转动。
念到「跑得飞快」时车身滑动速度最快一次强调。
念到「keyword」时速度线密集喷射一次强调。
念完段 N 后画面短暂呼吸。
```

### 对比

| 写法 | 效果 | 适用场景 |
|------|------|----------|
| ❌ 速度线从尾部向后喷射划过，念到「bullet train」时变密集 | 默认静止，只在触发点动一下 | 普通触发式动作 |
| ❌ 速度线持续喷射、车身持续快速前后摆动 | 原地振动，没有前进感 | 生物类（第一轮修复） |
| ✅ 车身从右侧向左侧快速滑动穿过画面，速度线持续喷射 | 从开头就持续前进，触发点达到峰值 | 车辆类（第二轮修复） |

### 常见持续语义旁白

| 旁白 | 持续动作 | 触发峰值 | 表现手法 |
|------|----------|----------|----------|
| 「高铁跑得飞快，bullet train！」 | 速度线持续喷射、车身从右向左快速滑动 | 念到「跑得飞快」时滑动最快 | 滑动法 |
| 「旗鱼游得飞快，sailfish」 | 水花持续喷射、身体持续快速摆动 | 念到「游得飞快」时最密集 | 振动法 |
| 「推土机推泥土，bulldozer」 | 铲子持续推土、泥土持续隆起 | 念到「推泥土」时力度最大 | 振动法 |
| 「风车一直转，windmill」 | 风车持续旋转 | 念到「一直转」时速度最快 | 振动法 |

### 反模式

- ❌ 旁白说「跑得飞快」但镜头只写「轻微前后摆动」（力度不够）
- ❌ 旁白说「跑得飞快」但动作只在末尾触发一次（没有持续感）
- ❌ 旁白说「跑得飞快」但速度线只喷一次（不是持续喷射）
- ❌ 车辆类旁白说「跑得飞快」但只用振动法（没有前进感，用户会打回）
- ✅ 车辆类旁白说「跑得飞快」→ 滑动法（从右向左快速滑动）+ 速度线持续喷射 + 念到关键词时达到峰值


### 23.1 A2A 批量 ≠ 本会话独占管线 —— 回执前必核对 task 唯一性

**实测事件**：本会话提交 8 个 task 后 34 秒，tasks.json 里又冒出另一组 8 个 task_id（网关查证全部真实 succeeded）＝同批任务被双份提交（疑似 peer 侧并行触发），涉及重复计费。另注意 submit 脚本对提交失败会记 `{'clip': n, 'error': ...}` 无 task_id 条目——统计时先过滤。

**防护三步（写进回执流程）**：
1. 每次 submit 轮后核对 tasks.json 里含 task_id 的条数 == 预期 clip 数（submit 脚本是 append 制，自身不去重）。
2. 下载/合成前逐一核对已下载文件 ↔ 本会话提交的 task_id。⚠️ poll 脚本惯用法 `status_map = {t['clip']: t for t in tasks}` 是 dict 后值覆盖——tasks.json 有重复条目时会**静默换绑到后一批**并按后批下载。
3. 出现未知 task_id 时先 `GET {ARK_BASE_URL}/{task_id}` 向网关确认真伪，回执里把两组 task_id+时间戳并列如实报给 peer 核计费，不擅自隐藏。

### 23.2 成片合成 v2 = 原生完整时长 concat 直拼（清洁工批次沉淀、本批复核的现行标准）

- 旧 v1（按 SRT 裁齐 trim + tpad 补帧）实测产物：2.08s 画面冻结 + 死寂洞 + 末段 clip 被截短——用户否决，已弃用。
- **v2**：`ffmpeg -f concat -safe 0 -i list.txt` 8 clip 原生完整时长直拼，无 tpad / 无截断 / 无转场 / 无 BGM，crf18 24fps + aac192k 48k `+faststart`。总时长 = Σ 原生时长（本批 35.78s），SRT 总跨度（约 31~33s）只作参考不作硬裁依据。等效变体（工程师批 39.71s/16.7MB 过验）：8 个 `-i` 输入 + `concat=n=8:v=1:a=1` filter_complex 直拼同参数出片，无 list.txt；两形态任选。
- clip 时长指派 = `ceil(SRT 段跨度)`（合并句按跨度和），禁加戏；短叹词句（如段9/段11「dancer！」）保留在所属 clip 原生音频里，勿剪。

### 23.3 发音自检：先查 faster-whisper 再说"无法自检"

- peer 指令常假设"本机无 whisper"——不要照抄进回执。实测 openai-whisper 无，但上一批遗留 asr_venv 里有 **faster-whisper + 已缓存 small 模型**，可直接做发音复核（本批 8/8 通过）。
- 判定口径（与清洁工批次一致）：核心词 ok = ASR 文本含词干变体任一（dancer/dance/danser/丹瑟…）；转写出 `Dancer/DANCER/Dancers` 大小写复数差异 = whisper 转写层噪声，不判失败。中文旁白核对核心词逐句在位。
- 批量 prompt 骨架沿用上一批 prompts/ 逐段改写：段 5 语速写死四要素（明显放慢/每字清晰/节奏舒缓/全片一致）+ IPA 重音首音节 + "严禁读成…任何变体"反变体禁令 + 旁白词禁入画面 ban 清单；多行 SRT 合并句写成"旁白共两句，先念…停顿一拍，再单独念…"。verify_prompt.py 8/8 零 FAIL 再提交。

### 23.4 并发会话同工作区：重合成竞态 + 回执数字时效（2026-08-31 牙医 v3 收尾实测）
- **双 build 竞态**：同一 /tmp 工作区有多个会话并行时，回执前 `ps aux | grep -E 'ffmpeg|build_final'` 查竞态——实测两个 build_final_dentist.py 同时在跑（两个 ffmpeg 同写 final_tmp.mp4），产物 md5 中途漂移且 freezedetect 中段误报 10.8s 长冻结；**串行重跑一次 concat 后假冻结消失**（只剩良性段尾静息，见 23.2）。凡 freezedetect 报「中段长冻结」且涉事 clip 单测干净/未复现 → 先怀疑并发构建产物损坏，串行重建复验，别急着判 clip 画面问题。
- **回执数字时效**：换入新 clip 后旧回执的 md5/直链/大小全作废。四步：①重跑 concat ②重新 upload_to_uguu ③**回下载直链（curl）→ md5 与本地比对一致**才报新直链，uguu 返回的 URL 不能默认可用 ④回执明示「旧 md5/旧直链作废」（牙医批：EHvxyOux 挂着不含真 v3 的旧 final，peer 可能拿上一条回执直链当最终版）。
- ASR 解释器定位/就绪轮询/离线跑、PASS 结论与工件版本绑定 → session-pitfalls（references/mask-mouth-final-review.md §B2/§B3）。

### 23.4 收尾工程三陷阱（2026-08-31 牙医实测）

1. **ASR 日志新鲜度**：log 里的 PASS ≠ 当前产物的 PASS——中途重摇/换版本后，旧 log 常被误当新版本转写（牙医批 asr_v3.log 的 PASS 实为 14:07 对 v2 重摇版的转写，真 v3 14:10 才落盘）。回执前核对 log mtime ≥ 产物部署 mtime，否则对当前落盘文件重跑；判定永远以“对现行文件实测”为准，不以历史日志为准。
2. **ASR 环境漂移重建**：默认 python3 无 faster-whisper 时不直接报“无法自检”——上批遗留 venv 或已缓存模型常在。重建一条龙（实测通）：`uv venv /tmp/asr_venv` → **去代理** + `uv pip install --python /tmp/asr_venv/bin/python --index-url https://pypi.tuna.tsinghua.edu.cn/simple faster-whisper`（官方源直连 >7min 必超时，清华镜像秒装）→ 运行加 `HF_HUB_OFFLINE=1 HF_ENDPOINT=https://hf-mirror.com`（模型已缓存 download_root 时离线直跑，顺带绕开 SOCKS 代理环境坑）。长跑放后台 + notify，前台 >420s 会被硬超时。**HF 缓存为空需首跑下载模型时的三坑（2026-08-31 doctor 批实测）**：①代理变量 `all_proxy=socks5://127.0.0.1:7890` + 小写 `http_proxy/https_proxy` 是 **uv run 注入子进程**的，shell `env`/`grep proxy` 看不到 → 脚本开头必须在 Python 内 `del os.environ[k]` 清掉全部 *proxy*，否则 huggingface_hub 走 SOCKS时报 httpx 缺 socksio；②`HF_ENDPOINT=https://hf-mirror.com` 必须在 import huggingface 前设置（直连 hf.co = Network unreachable）；③镜像走默认 Xet 下载会 401（cas-server.xethub.hf.co）→ 加 `HF_HUB_DISABLE_XET=1` 退普通 HTTP。三设置齐后 small 模型下载+转写一次跑通；缓存落 ~/.cache/huggingface/hub，之后可 `HF_HUB_OFFLINE=1` 离线直跑。判定脚本：语言用 language=None 自动检测，DOCTOR 判定 = 中文「医生」或词干 doctor 任一在位。
3. **并发产物对齐**：同批 A2A 任务可能被派给多个并行 agent——同目录 final_dentist.mp4 会互相替换（牙医批本会话 14:33 产物被另一路 14:39 重跑覆盖）。看到外来 ffmpeg/uv 进程**先等它结束再验收**，别抢跑覆盖；回执的 md5/大小/总时长/直链必须对“当前落盘文件”实测回读，多路回票时以同一文件指纹（md5）对齐。

## 24. 口罩漏嘴（旁白语义渗漏到人物）v3 修复策略（2026-08-31 牙医实测一次过）

**症状**：小牙医口罩上反复出现嘴/牙齿/口腔开口（v1、v2 三摇均复现，唯一验收项不过）。
**根因**：段 3 旁白动作词「张大嘴巴」的语义渗到画面人物身上——模型把“张嘴”渲染到戴口罩的牙医面部。负面约束只写一次压不住。

**v3 四件套（第 4 摇一次过）**：
1. **语义唯一绑定**：明写「张大嘴巴」表意对象只有桌上牙齿模型的上排牙齿向上抬起呈张开状，人物全身绝无任何口型、嘴唇被口罩完整覆盖。
2. **降低面部细节倾向**：人物改 45° 侧身站姿、四分之三侧脸只占画面很小部分、口罩纯色无图案且面积尽量小——脸上留白越多，模型越不会往上画嘴。
3. **负面约束原文整句 ×3**：「口罩是完整纯色布料，绝对没有嘴、没有牙齿、没有舌头、没有口腔、没有任何开口，从头到尾一帧都不变」在段 1 开头 / 段 2 末尾 / 段 3 结尾各一次（×1 实测不够）。
4. **保留已过项**：v2 已过项（双臂双手/桌面道具按参考图/牌面文字锁定/旁白逐字/音标与慢速/「叮」音效）原样保留，只追加新约束不改旧描述。

**复查法（8 帧放大拼表）**：0.5s 步进抽 8 帧 → 脸部-胸口区 3× 放大拼表，唯一验收 = 全帧口罩无嘴/牙/舌/口腔/开口且无消失移位。⚠️ 拼表前必须先**单帧放大确认裁切框真的包含目标小区域**（口罩/眼睛/牌面文字同理）——首版拼表框截高了（只有头发+眼睛，口罩在框外），vision 照样逐帧答“干净”，险些当有效证据交回执。牙医批完整配方（含裁切框坐标与提交脚本断言）：`references/mask-mouth-fix-v3-prompt.md`。

## 25. 物理抽帧复查通用配方（2026-08-31 医生批 clip5 重点项 + 全 8 clip 手臂数实测）

> §24 是「口罩漏嘴」专项修复；本节是 A2A peer 下发「物理抽帧复查」类任务的通用操作配方（重点 clip 逐项核 + 全 clip 手臂数/口型抽查）。

### 25.1 检查型 A2A 任务的工作区自主发现
peer 指令常引用裸路径（如 /tmp/pb_video4/videos/clip1~8.mp4），本会话 home 下 find 不到时按序定位：
1. **先 `session_search`**（主题词+sort newest）找上一轮同款请求——同批检查任务常被 peer 重发，历史会话里有全部工作区落点（/tmp/pb_video4/ 的 videos/ prompts/ SRT）；/tmp 工作区跨会话跨 agent 共享，直接复用。
2. 兜底：素材包本体在 `~/.hermes/cache/documents/doc_<hash>_视频.7z`，`7z l` 列内含 SRT 主题名（医生.srt/牙医.srt…）确认批次归属。
3. 历史已有 PASS 结论也**必须对当前落盘文件重跑实测**（同 23.4 条 1：历史 log ≠ 现行产物），只复用路径与工作区，不复用结论。

### 25.2 ffmpeg 抽帧写法（实测可用）
```bash
# ✅ 按秒抽单帧（稳）
ffmpeg -y -v error -ss 1.5 -i clipN.mp4 -frames:v 1 out.png
# ❌ select 双输出（image2 muxer 报 Cannot write more than one file with the same name）
ffmpeg -i clipN.mp4 -vf "select='eq(n,20)+eq(n,70)'" -vsync 0 a.png b.png
```
抽帧点：常规 clip 抽 2 帧（20f/70f 或 0.5×/0.85× 时长）；重点 clip 按 0.5s 步进抽 4-6 帧看动作弧线（如男孩张嘴渐大、压舌板胸前→触唇→入口的渐进），动作弧线是区分「动作按节拍推进」与「瞬移/跳变」的关键证据。

### 25.3 拼表自检：交 vision 前先验拼表本身
- **拼图画布宽度必须按 len(files) 动态算**——本批自制 montage 函数硬编码 4 列宽，6 帧的第 5/6 帧 paste 到画布外被裁掉，vision 报「图中实际只有4帧」。vision 的帧数读数是准的，错在拼图越界。
- vision 报「帧数/内容与预期不符」时**先怀疑拼表 bug（越界/裁切框错）再怀疑幻觉**——与 §24「裁切框截高致口罩在框外」同一族教训：交 vision 的证据物要先自检完整。
- 每张拼表 ≤4 帧（324×576 缩放、标签写帧上方、白底）；抽的帧多就多拼几张或对关键帧单独 vision。重点项（口型/器具）除拼表外对关键帧单帧补验 1-2 张交叉确认。

### 25.4 边缘判定项：多帧交叉 + 回执如实报分歧
vision 对器具形状这类边缘项判定不稳定（医生批 clip5 压舌板：拼表判定「勺/桨状压舌板 PASS」，单帧复验却判「椭圆勺头形似木勺 FAIL 形状项」）。处理：①边缘项不凭单帧单次判定，≥2 帧交叉；②回执如实写「两次判定 1 过 1 报形状存疑」+ 客观事实（椭圆头、位置/数量/动作全部正常），是否算过交 peer 裁，**不擅自抹平分歧改判**。

### 25.5 回执格式纪律
peer 明示「只回逐clip一行：过/不过+不过原因」→ 逐 clip 严格一行 + 一行总结 + 唯一存疑项 ⚠️ 备注标明「是否算过由你裁」；不写流程叙述、不贴帧清单。（同族：§23.1 回执如实报、§23.4 数字对当前落盘文件实测回读。）

### 25.6 复查对象字节一致性 —— 多写者工作区验收五查（2026-08-31 医生批 final 验证实测）

peer 复查请求自带**过去时断言**（「clip8 v2 已落盘 16:58 已复查」「final 已重合成 md5=3d9ac135…」）。实测到验收时点：clip8 已被并发会话再换 2 版（17:13 锁定 d9hft 半身 → 17:21 golden w8jc4 全身）、final 重编 2 次（3d8bf805→c217ebb3→81ae7069）、所述 md5 全盘不存在、历史帧目录抽的是已废弃字节。验收前五查：

1. **断言对盘**：peer 给的 md5 先全盘 sweep（`find /tmp /home/ubuntu -name '*.mp4' -newermt <任务起点> | xargs md5sum`）；盘上没有 → 如实报「不存在」+ 实际重编链（md5+mtime），不脑补「哪一版应该就是」。
2. **帧目录绑字节**：复用历史 montage/帧目录前先按 mtime 认定它抽自哪版字节；新抽帧目录名用 `recheckN_<md5前8位>/`，禁用版本绰号——本例 17:21 名为 d9hft 的抽帧目录实际装着 w8jc4 字节，vision 结论险些错绑版本。
   **像素级实证绑定（2026-08-31 clip8 复查再战实测，推荐升级）**：mtime 只是旁证，PIL 像素差可直接实证——对候选 mp4 在帧目录同时间点 `ffmpeg -ss <同秒>` 重抽帧，`ImageChops.difference(...)` 求 maxdiff：maxdiff=0 且 bbox=None = 同版字节实证绑定；maxdiff 200+ 全幅差 = 异版。一帧即可定版，3 帧更稳（0.2s/中点/末段）。实测用此法一次厘清 4 个候选 clip 与 4 个历史帧目录的版本矩阵（d9hft=clobber、recheck_fresh=golden），并确认历史 recheck8_d9hft 目录确实绑定 d9hft 字节。
3. **名实核对**：文件名（…_clobber/…_golden/…_final）仅供参考，裁决只看 md5sum；工作区 task_*.txt 的 lock/void 批注行是并发兄弟会话的最新裁定，动手前先读（本例「passed-9frame take = d9hft / void: fb6e6b69 fullbody」就写在批注里）。
4. **报告冻结时点**：验收报告开头记 `date` 快照 + `ps aux | grep [f]fmpeg` 为空才验收；有并发 build 在跑就等结束，不与 ffmpeg 抢同一产物。
5. **裁决冲突如实并列**：锁定版是半身 d9hft、final 却编入全身 w8jc4 这类两说 → 回执两案并列（各附 md5/SSIM 证据 + 建议）交 peer 裁，不擅自定案、不悄悄改产物。

### 25.7 final 验收三件新招（2026-08-31 医生批实测）

- **SSIM 鉴定 final 内嵌 clip 版本**——md5 只能告诉你 final 变没变，SSIM 才能告诉你变进去的是哪一版 clip：final 末段对候选取逐帧 SSIM，All≈0.99+ = 同版，≈0.6x = 异版（不同镜头）。
```bash
ffmpeg -v error -ss <前N-1段原生时长和> -t <clip时长> -i final.mp4 -i candidate_clip.mp4 \
  -lavfi "[0:v][1:v]ssim" -f null -
```
- **freeze 细档**：`freezedetect=n=-60dB:d=0.1`（d=0.5 会漏短冻结）零输出 + 末段抽 3-4 帧哈希互异 = 「无尾部冻结」双证据；帧级证据远比肉眼看末帧「好像一样」可靠。
- **9 帧均匀抽帧 × 3×3 拼表**（构图类复查：半身/全身、腿脚、悬浮、文字四问一次判）：0.2s 起步长 0.45s 抽 9 帧 → 逐帧 `scale=440:-1` → hstack3+vstack3 交 vision；判例：底边裁在髋部 = 半身，见鞋/袜/小腿 = 全身，「髋部一条裤边」不算腿脚；小孩单脚跳/抬腿+脚下有影 = 自然动作非悬浮。判定永远绑字节版本（§25.6-2）。
- **回传链接双向时效**：工作区里兄弟会话留下的 uguu 直链别默认是新版——curl 回来 `md5sum` 对现行产物再引用（实测旧直链挂着 17:15 旧拷贝，md5 已过时两个版本）。**上传侧同样要验（2026-08-31 再战实测）**：`uguu_final_url*.txt` 可能对应一次**实际失败**的上传——本例 uguu_upload_resp_v4.json 是 `success:false errorcode:500`，URL txt 却照样落盘，curl 回来 md5 不符；引用任何继承的 URL txt 前先看配对 resp json 是否 success:true。uguu 偶发 500 → 直接重传即成功：`curl -s -F "files[]=@clipN.mp4" https://uguu.se/upload`，以 resp `success:true` + 回下载 md5 一致为准，成功后才写 URL txt。

### 25.8 抽帧标注戳 ≠ 画面内文字 ——「第三行文字」假阳性 + 文字项裁决纪律（2026-08-31 工程师批实测）

- **症状**：check_frames/frames_m 抽帧左上角出现「白底红字 `_0.20s`」/「`c4_f4_5.90s`」标注，险些判成画面内第三行文字/水印 FAIL——vision 裁决文字行数直接用了这些带标注帧。
- **定性特征**：标注内容恰好等于帧文件名（c4_f4_5.90s ↔ c4_f4_5.90s.jpg）、白矩形底框 + 圆润无衬线红字（DejaVu/matplotlib 族渲染特征）、紧贴边角机械对齐、边缘锐利无视频压缩噪点 → 全是抽帧脚本后期叠加的角标，**视频流内不存在**。
- **铁律**：文字行数/多余字符/水印类裁决必须用**干净重抽的无标注帧**（`ffmpeg -ss <t> -i clipN.mp4 -frames:v 1 verify_*.jpg`）；带标注帧只用于构图/肢体/动作裁决。一步定性：同秒干净重抽 + vision 放大（用 region 参数 [x1,y1,x2,y2] 原图坐标裁小区域）→ 干净帧无标注 = 工具角标实锤，源视频无违规。
- 本批实测：clip2/clip4 帧「_0.20s」「c4_f4_5.90s」标注全部定性为工具角标，干净重抽后画面均为恰好两行（小写 engineer + 工程师）。

### 25.9 半身 clip 下摇露脚 / 单帧「文字丢失」/ 尾帧重影 —— 工程师批三发现

- **半身构图铁律的「静帧达标、过程下摇」骗术**：clip5（铁律=头部到大腿根、腿脚绝不入画）start 帧构图**下摇露全身**——头顶画出上缘、双腿+卷边裤脚+鞋全部入画。半身验收不能只看中段帧「裁到哪儿」，start/mid/end 三帧都要验露脚与否；露鞋=violation，不管中段多标准。
- **单帧「无文字」≠ 文字丢失**：clip6 mid 帧 vision 报「画面无 engineer/工程师」，只有卷尺数字。文字压在腿前、与腿同色系时 vision 漏读率高——单帧缺失不判 FAIL，≥2 帧交叉（含文字应在位置附近帧）后仍缺才写 ⚠️；未交叉的先 ⚠️ 待复核，不单方定案（§25.4 同族）。
- **尾帧重复人脸伪影**：clip4（6.08s）5.9s 帧人物纵向重复 ×2 + 第二行不完整 engineer 底缘被裁（双影），5.7s 干净——伪影只占尾部 ~0.2s。动作弧线抽查（§25.2）覆盖 start/mid 之外，**收尾判定帧取 dur-0.2s 级别的真末帧**，不然尾段伪影漏检；查出后按帧区间如实报（「≥5.9s 双影、5.7s 干净」）。

### 25.10 「final 晚于所有 clip mtime」≠「final 含新版」——终验采信规则（2026-08-31 工程师批 peer 收尾三件实测）

peer 收尾断言形如：「20:31 重拼晚于全部 clip mtime（clip2 20:29 最晚）→ 应已含 clip2 v4/clip8_v2/clip4,5,6 重生成版；ASR+物理复查记录在案 → 全过没？md5 若 differ 以新为准」。实测三段推理全翻车，收尾验收按以下五条采信：

1. **mtime 链推理不裁决「final 含哪版 clip」**——重拼时刻晚只说明拼得新，builder 用旧源照样产出新 mtime。实测 PIL 滑动对齐定版：final∩round1/clip2（旧版）平均差 **10.4**、∩clip2_v3 **39.3**、∩clip2_v4 **34.2** → 20:31 final 里装的是**旧 clip2**，「应已含 v4」为假。裁决只认内容鉴定：SSIM（§25.7，≈0.99 同版 / 0.6x 异版）或 PIL 滑动对齐法——final 内 clip 起点未知时，候选 clip 在自身时间线抽 3-4 参考帧（如 0.5/1.5/2.5/3.5s），final 在 t0∈[预测起点±0.6s] 以 0.1s 步进滑窗，每个 t0 对同偏移帧求 ImageChops 平均差（无 numpy 用 histogram 加权均值），全窗最小值 = 定版 + 顺带定位 clip 起点与 clip 时长（源 clip 时长 ≠ final 中段长时尤其要先测时长再定窗）。判据：同版 ≈10，异版 30+。**「md5 若 differ 以新为准」同理只回答「变没变」，不回答「变对没」——新 ≠ 对，先内容鉴定再定以哪个为准。**
2. **判定登记簿按字节采信，不按批次采信**：asr_results_final.json / physcheck_results.txt 的 mtime 早于 clip 最新重生成 → 对终版 clip 集整体过时；但先找 per-clip 复测件再定「未验」——本例 asr_c2v3.json 20:33 / asr_c2v4.json 20:38 均晚于 clip2_v4 生成 20:36 → clip2 的 ASR 可采信复测件；两者皆缺的项目（本例 clip8_v2 20:29 重生成无帧检记录）= 对终版**未验**，回执写「未验」不套旧 PASS（细化 §23.4-1）。
3. **物理复查是逐帧逐项清单，不整体二元化**：记录里混着「c8v2 末帧接触阴影消失」「r2clip8_mid 屈膝腾空姿势」这类未平掉项时，回执逐项列原话交 peer 裁，不汇总成「全过/全不过」（§25.4 同族）。
4. **ASR 中文叠字按层面归因**：clip1 转写「工程程师」+ zh_ok=false，属 seedance-prompt-pitfalls 已载的中文滑音/吞字判例族（**音频层**）；帧检无叠影只排除画面重影，排除不了发音问题——回执注明层面（音频层待回听/交 peer 裁），别归为画面问题，也别替音频盖章 PASS。
5. **uguu resp 的 `hash` 字段不可当文件哈希**：16 hex 与 md5/sha256 前 16 位/crc32 全对不上（系内部存储键），直接忽略；上传可信度唯一判据仍是回下载 md5 一致（§25.7）。

**本机 ops 旁注**：本 agent 自己进程写入 /tmp 的中间产物（抽帧 png 等）实测**即写即不可见/不持久（即便命令 rc=0）**，同一调用内也可能失败；写 /home/ubuntu 则始终持久；读他人 /tmp 工作区正常。跨调用要复用/比对的中间文件一律落 /home/ubuntu/，且「抽帧+比对」尽量合并进一次调用内完成。

## 26. A2A 批进度速查协议 — 跨会话三源事实核查（2026-08-31 工程师批实测）

> peer 下发「进度速查」类任务（"N 条 prompt 写完提交没（task_id）？落盘几个 clip？合成/自检到哪？只回事实"）。批 worker 跑在**另一条并发会话**里（state.db 里 title 形如「pb_video5 批次8条视频一条龙生成」），本会话 home 下 find 常查不到它的落盘痕迹——必须三源合查，逐问给数，不写流程叙述。速查是**只读**动作：不动工作区文件、不 kill 任何进程（孤儿排雷只属于收尾重跑场景，见 session-pitfalls）。

### 26.1 三源核查（按序）

1. **盘**：批工作区在 `/tmp/pb_video<N>/`（/tmp 是 /tmp，home 递归 find 会漏；`ls -lt /tmp` 直接看）。工作区目录名与批次对应（pb_video4=医生批、pb_video5=工程师批），找不到时用 §25.1 兜底（素材 7z 的 SRT 主题名定批次）。
   - `ls -la /tmp/pb_video<N>/` + `find /tmp/pb_video<N> \( -name '*.mp4' -o -name '*prompt*' -o -name 'tasks.json' \)`
   - 产物进度直接读目录：image-inventory.md / crop2x / preview(montage) = 仍在 Step 2/5 写前核对；prompt_clipN.txt 或 prompts/ = Step 5 已产出；clips/*.mp4 = 已落盘 clip；final*.mp4 + uguu_* = 已合成/上传。**文件数就是回执里的数**（0/8 prompts、N 个 clip…），别目测。
2. **并发 worker 会话**：读 `~/.hermes/state.db`（建议走 execute_code 跑 sqlite；terminal heredoc 同款查询会被 gateway 安全启发式误拦报 "cannot restart the gateway"，换 execute_code 即过）：
   - 定位：`SELECT id,title,datetime(last_activity_at,'unixepoch','+8 hours') a,message_count FROM sessions ORDER BY last_activity_at DESC LIMIT 10`（sessions 表**没有** updated_at 列，用 last_activity_at；title 含批次主题词）。
   - 读实时进度：`SELECT role,tool_name,substr(content,1,400),datetime(timestamp,'unixepoch','+8 hours) FROM messages WHERE session_id='<id>' ORDER BY timestamp DESC LIMIT 15`——assistant 行 content 为空而 tool_calls 非空 = 在途调用，tool_calls 的 JSONB arguments 能看到 worker 正在核哪张图/哪一步；最近活动时间戳 = alive 还是卡死（回执里报给 peer）。
   - 历史批次结论/上一步到哪：该会话的 tool 输出即事实源，比猜文件名可靠。
3. **进程**：`ps aux | grep -E 'ffmpeg|seedance|submit|asr|concat' | grep -v grep` ——「合成/自检到哪」必须有进程级佐证：无产物 + 无进程 = 未开始；有 ffmpeg 在跑 = 合成中或并发 worker 在动这个产物（此时按 §25.6-4 等结束再验收）。

### 26.2 回执格式

对齐 peer 四问逐条给数：① prompt N/N 写完、提交无/有（task_id 列出）② clip 落盘 N 个 ③ 合成/自检状态 + 进程佐证 ④ worker 会话最近活动时间戳（alive 判断）。上一批若已收尾（final*.mp4 + uguu 回执在位），末行附一句事实。其余同 §25.5：只回事实，无流程叙述、无推测。

## 27. delegate 子任务纪律：clip 划分落盘 + L3 审查数据内联（2026-09-02 消防员批实测）

### 27.1 `clip_merger.py` 只打印 stdout，不写 clips.json

跑完 `python3 scripts/clip_merger.py timeline.json --user-tts N` 后**立即重定向落盘**：`> clips.json`。后续 delegate L3 审查、跨会话续做、提交核对全靠这个文件——第一轮 L3 审查子 agent 因找不到 clips.json（全盘 grep 误入西兰花/黄瓜/茄子等历史项目目录），600s 预算全部耗尽在搜索上，零产出超时。

### 27.2 L3 审查 delegate 必须数据内联 + 限预算

重发成功版（96s 全 PASS，2 次 API 调用）的任务结构：
- **任务文本直接内联**：clip 划分（段号/时长/srt_span）+ 全部 8 段旁白原文 + 审查清单（6 项逐项 PASS/FAIL）
- **显式限令**：「只读 N 个 prompt 文件、严禁全盘搜索、≤10 次工具调用、10 分钟内出结论」
- 输出格式要求写死：每 clip 一节 + 总结论 ok/not-ok + 问题清单
- 反例对照：笼统交代"clip 划分在 clips.json"+不设预算 → 子 agent 自主探索 18 次调用 600s 超时；steer 纠偏送达有延迟（当前工具调用不中断），救不了已跑偏的探索路径
- steer 补数据仍值得发（子 agent 下个工具结果就能看到），但**重发内联版比等 steer 更可靠**
