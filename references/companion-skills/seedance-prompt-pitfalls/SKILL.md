# Seedance 2.0 Prompt 陷阱库

> **定位**: picturebook-video 的 companion skill。当 picturebook-video 的 Step 5 写 prompt 时，**必须先加载本 skill 检查是否有适用的陷阱规则**。
>
> **来源**: 2026-07-30 Storm暴风雨 / Summer Solstice夏至 实测对比（Seedance 2.0 vs 之前 GLM 模型）
>
> **渠道/部署陷阱**: seedance MCP 的 401 / verify_api_key 假阴性 / 跨电脑 wrapper 自动探测，见 `references/seedance-channel-wrapper-pitfall.md`（2026-08-24 换渠道实测）。
>
> **段1 描述细节漂移陷阱**: 写段 1 逐图描述时凭记忆重写文字位置(上 vs 正下方)/人物外观件数(丸子头、连衣裙一件式) → 与参考图不符、L3 独立 vision 复核抓出。见 `references/duan-1-detail-drift.md`（2026-08-27 胡萝卜实测）。铁律：**段1 细节必须逐字照抄 Step 2 vision 记录，禁止凭印象重写**。

## 陷阱 #18：人物眼神呆滞 / 表情空洞（2026-08-29 画家实测）

### 问题

用户反馈视频中人物"表情眼神呆滞"，但视觉模型抽帧分析显示"眼睛有高光、表情微笑、不呆滞"。用户与视觉模型的判断不一致。

### 根因

1. **静态截图 vs 动态视频的感知差异**：视觉模型看的是单帧静态截图，能检测到高光/微笑等特征；但用户看的是**连续动态视频**，如果人物在整个镜头中没有**动态表情变化**（眨眼、眼珠转动、嘴角变化），在动态观看时会显得"呆滞/空洞"——即使单帧表情本身是OK的。
2. **Seedance 默认不做微表情动画**：如果不显式写眼部动作，Seedance 倾向于保持参考图的静态表情不动，整个镜头中人物"像照片一样"没有生命感。

### 修复方案

在段 2 主体动作序列的**每个镜头**中，显式写**眼部动作 + 面部微变化**：

```markdown
❌ 缺少眼部动作（静态表情 → 动态观看显呆滞）：
镜头 1：缓慢推镜，男画家左手轻触头顶贝雷帽微微按压，身体微微前倾靠近画面中央。

✅ 加眼部动作（动态表情 → 有生命感）：
镜头 1：缓慢推镜，男画家左手轻触头顶贝雷帽微微按压，身体微微前倾靠近画面中央，眼睛眨动一下，眼珠微微转动。
镜头 2：横移从左向右，小男孩画笔搅拌调色盘，眼睛眨动一下，嘴角上扬。
```

**关键词**：`眼睛眨动一下`、`眼珠微微转动`、`眼珠灵动转向观众`、`嘴角上扬`。每个镜头至少写一个眼部动作。

### 适用范围

所有**人物正面/半正面构图**的 clip，尤其：
- 职业认知类绘本（画家/医生/消防员等，人物占画面主体）
- 近景/中近景镜头（人物面部占画面比例大，呆滞更明显）
- 全身/远景中人物面部占比小 → 可不加（呆滞感知弱）

### 反模式

- ❌ 视觉模型说"有高光、不呆滞"就不修 → 视觉模型看单帧，用户看动态
- ❌ 只在段 1 写"大眼睛带高光，表情微笑" → 段 1 是静态描述，不产生动态表情
- ✅ 段 2 每个镜头都加 `眼睛眨动一下` + `眼珠微微转动/嘴角上扬`

## 陷阱 #19：旁白动作语义渗到遮挡物——「张嘴」被画到口罩上（2026-08-31 牙医实测）

### 问题

clip3 旁白「牙医说张大嘴巴，dentist」，画面人物是戴口罩举牌讲解的小牙医。v1/v2 连续两版都在 1.5s 后把**张开的嘴（白牙+舌头+口腔）直接叠画在口罩上**，像口罩破洞——物理（口罩必须完整遮口鼻）+逻辑（旁白是牙医让病人张嘴，不是牙医自己张）双重不合理，且一直持续到片尾。

### 根因

**旁白动作动词语义渗透**：generate_audio=true 时模型解析旁白文本，「张大嘴巴」需要可见载体，人物嘴被口罩遮住无处安放 → 渗到画面上最像「嘴」的部位 = 口罩。v1 段2「向嘴边比一个张大的口型」直接诱导；v2 删了比口型、加了口罩负面约束（1 次），但「张大嘴巴」仍在旁白里，渗漏照旧——**负面约束只写 1 次压不住**。

### 修复策略（v3 一次过 · 4 层）

1. **语义唯一绑定**：「张大嘴巴」的表意对象显式绑定到桌上牙齿模型（上排抬起呈张开状、念到时抬更高一点），人物全身绝无任何口型。段 1/段 2/段 3 都写。
2. **降低人物面部细节倾向**：人物改 45 度侧身 + 四分之三侧脸 + 面部只占画面小部分 + 口罩纯色小面积无图案——侧脸让「口罩后面有嘴」无想象空间。
3. **负面约束字面原文重复 3 次**（段 1 开头 / 段 2 末尾 / 段 3 结尾各一次，一字不差）：「口罩是完整纯色布料，绝对没有嘴、没有牙齿、没有舌头、没有口腔、没有任何开口，从头到尾一帧都不变」。
4. 已过项（双臂双手/桌面道具/牌面文字/旁白逐字/音标/慢速/禁BGM/音效）原样保留，只加不改。

### 验收纪律

硬伤项单独验收：8 帧 @0.5s + **口罩区 3 倍放大拼表**。⚠️ 先单帧确认裁切框真的包含口罩再拼表——裁到眼睛高度会得到「8 帧全部干净」的**假阴性**（口罩根本不在框内）。逐帧查无嘴/牙/舌/口腔/开口 + 无口罩消失移位；已过项不重复报。

### 适用范围

所有「旁白含身体/口型动作动词 + 人物面部被遮挡（口罩/头巾/面罩/围巾）」的 clip：医生、护士、厨师、防疫、戴口罩职业装等。特征 = ① 旁白动作词的可见载体与人物遮挡冲突 → 语义必然渗透。预防：写 prompt 前先过一遍旁白里的每个动作动词，把它的表意对象显式绑定到一个**可见且物理合理**的画面元素上。

## 陷阱 #1：旁白文字被渲染为画面元素（2026-07-30 实测）

### 问题

Seedance 2.0 会将 prompt 中引号内的旁白原文当作画面装饰文字渲染到视频帧上。

| 参考图原有文字 | 生成画面出现的新文字 | 来源 |
|---|---|---|
| 1.jpg 有"暴风雨"（白色） | 画面出现"黑马云"（彩色） | prompt 段3/段5 中的旁白原文被渲染 |
| 3.jpg 有"暴风雨" | 画面出现"闪电亮"（彩色） | 同上 |

### 根因

Seedance 2.0 是多模态模型，prompt 中引号内的任何文本都可能被它理解为"需要在画面上显示的文字内容"。这与 GLM 模型不同——GLM 把旁白文本理解为纯音频指令，不渲染到画面。

### 修复方案

**段 3 · 旁白-动作对应** 改为只写动作映射，不写旁白原文：

```markdown
❌ 错误（旁白原文会被渲染到画面）：
段 1 念"暴风雨 STORM！"：乌云翻涌 + 闪电劈下穿O

✅ 正确（只写动作映射，不写原文）：
段 1：乌云翻涌 + 闪电劈下穿O + 字母弹跳对应"STORM"
```

**段 5 · 音频描述** 改为只写音效，不写人声旁白文本：

```markdown
❌ 错误（人声旁白原文会被渲染到画面）：
人声旁白："暴风雨 STORM！" — 温柔女声...
音效：乌云翻涌时配低沉"轰隆"声

✅ 正确（只写音效，人声旁白由 MiniMax TTS 独立生成）：
音效：乌云翻涌时配低沉"轰隆"声，闪电劈下时配"噼啪"声
```

### ⚠️ 段3 完整中文旁白 = 顽固污染源，且与 verify_prompt R8 冲突（2026-08-19 爆米花实测）

**根因补全**：污染汉字不仅来自段5 人声旁白行，**段3 旁白-动作对应里写的完整中文旁白原文也会被 seedance 提取渲染**。爆米花绘本：段3 写 `段2念"玉米做的爆米花，popcorn"` → 画面标题「爆米花」被旁白词「玉米做的」覆盖成「玉米做的爆米花」。段1+段3+末尾**三处声明 + L4「画面只有两行文字」最强约束都写了仍失败**——因为污染源就藏在段3 引号内的中文旁白本身。

**与 verify_prompt R8 的冲突**：R8 硬性要求段3 必须有 `段N念"完整旁白"` 格式（正则 `段\s*\d+\s*念["\u201c\u201d']`），但写完整中文旁白又引入污染。**解法 = 段3 只写英文核心词，不写中文旁白**：
```markdown
✅ 通过 R8 且不引入中文污染词：
段1念"POPCORN"：爆米花堆轻微晃动，画面文字保持「POPCORN/爆米花」两行
段2念"popcorn"：玉米粒微闪、爆米花轻晃，画面文字保持「popcorn/爆米花」两行
❌ 污染（R8 虽过但中文被渲染）：
段2念"玉米做的爆米花，popcorn"：玉米粒微闪、爆米花轻晃
```
英文核心词 `段N念"POPCORN"` 同时满足 R8 正则和陷阱 #1 的"不写中文旁白"原则。**铁律：段3 引号内一律只写英文核心词（POPCORN/popcorn/ice cream），任何汉字（尤其句首修饰词：玉米做的/一大盘/淋在蛋糕上/小动物/巧克力/草莓）都可能被 seedance 渲染成画面标题**。R8 只检查格式不检查语言，英文核心词同样通过。

### 为什么"无字幕"约束不够

prompt 末尾的 `无字幕、无 Logo、无水印、无背景音乐` 只防了"字幕条"格式，但 Seedance 把旁白文本渲染为**装饰性文字元素**（像参考图中的标题文字一样），不是字幕条格式，所以约束不生效。

### 轻量级修复（2026-08-03 雨绘本实测有效）

在 prompt 末尾约束中追加：

```
禁止生成任何额外文字或字符，只保留参考图中已有的文字元素。
```

完整末尾约束示例：
```
无字幕、无Logo、无水印、无背景音乐。禁止生成任何额外文字或字符，只保留参考图中已有的文字元素。
```

**注意**：这个轻量级修复不需要修改段3/段5的结构，只需在末尾加一句话。如果轻量级修复无效，再回退到完整修复方案（去掉段3/段5的旁白原文）。

### 额外文字渲染的另一种机制（2026-08-03 雨绘本实测）

**现象**：旁白段8念"我喜欢下雨，rain！" → Seedance 在画面中渲染出"喜"字（从"喜欢"提取）。

**根因**：Seedance 2.0 不仅从 prompt 引号内文本提取文字，还会从 `generate_audio=true` 的旁白音频文本中提取汉字字符渲染到画面。这是**音频文本解析**机制，不是 prompt 文本渲染。

**修复**：同样使用轻量级修复——末尾加 `禁止生成任何额外文字或字符，只保留参考图中已有的文字元素`。这条约束同时覆盖 prompt 文本渲染和音频文本解析两种机制。

### 第三种机制：旁白词被"混入"参考图标题文字（2026-08-18 饼干 Biscuits 实测）

**现象**：参考图4 标题是 `biscuits`（全小写），但生成视频中图4 段落标题变成 **"小动动uits"**，中文也多了"小动动"——旁白"小动物饼干"里的"小动物"被 Seedance 混进了标题文字，把 `biscuits` 的前缀 `bis` 替换成了"小动动"。

**根因**：这是**旁白词污染参考图标题**的机制——Seedance 把旁白里的名词（"小动物"）当作画面标题的一部分，与参考图原有标题文字融合/替换，而不是像陷阱 #1 那样新增独立文字。多图 clip 中某张图标题文字较短时（如 `biscuits` 8 字母）尤其容易发生。

**修复**：在 prompt 段 1 描述该图时**显式声明标题文字完整内容**，并在末尾约束追加禁止混入旁白词：
```markdown
段1 图4：白色圆盘上摆着小熊/兔子/鱼/星星形状饼干，薄荷绿背景。上方彩色"biscuits"字母（全小写），下方黑色"饼干"二字。保留参考图中的"biscuits"和"饼干"文字作为画面元素，不要添加或替换任何文字。
末尾约束：保留参考图中的"biscuits"和"饼干"文字作为画面元素。禁止生成任何额外文字或字符，禁止把旁白中的词语混入标题文字，只保留参考图中已有的文字元素。无水印、无背景音乐。
```

**验证**：Step 7 抽帧时**逐图核对标题文字**，不能只看主体。若某图标题被旁白词污染（如"小动动uits"），需重做该 clip 并在 prompt 段 1 + 末尾约束双重声明标题完整内容。

### 第四种机制：旁白中文词整行覆盖标题，英文完全消失（2026-08-18 蛋糕 Cake 实测）

**现象**：参考图标题是 `cake`（小写）+ `蛋糕`，但生成视频中多个段落标题被旁白中文词**整行覆盖**，英文 `cake` 完全消失：
- 图3 段「一块三角蛋糕」→ 标题变成「一块三角」（英文 cake 没了）
- 图4 段「巧克力蛋糕」→ 标题变成「巧克力蛋糕」（英文 cake 没了）
- 图6 段「蛋糕上有蜡烛」→ 中文变成「蜡烛」（cake 保留但中文被换）
- 图7 段「一起切蛋糕」→ 中文变成「切蛋糕」（cake 保留但中文被换）

**与饼干案例的区别**：饼干是英文 `biscuits` 被**部分替换**成"小动动uits"；蛋糕是**整行标题被旁白中文词覆盖、英文完全消失**。这是同一"旁白词污染标题"机制更严重的表现。

**关键特征**：
1. **污染逐图独立**——同一 clip 里有的图对（图1/2/5 正确）、有的图错（图3/4/6/7 被污染），不是全 clip 一起错。Step 7 必须**逐图**核对，不能抽查一张就下结论。
2. **末尾加"禁止添加或改动任何文字"仍可能污染**——蛋糕案例 prompt 末尾已写「禁止大小写互相变形；画面文字严格保留参考图中的"cake"和"蛋糕"，不得添加或改动任何文字」，图3/4/6/7 仍被覆盖。说明**轻量级末尾约束对"旁白词覆盖标题"机制不够**，必须回退到完整修复：段 1 逐图显式声明标题完整内容 + 段 3 旁白-动作对应处也声明「画面文字保持参考图的 X，禁止出现旁白词 Y」。
3. **旁白里的中文名词（一块三角/巧克力/蜡烛/切蛋糕）最容易污染标题**——这些词跟标题文字同属"食物/动作"语义域，Seedance 倾向把它们并进标题。

**修复**：重做被污染 clip，在 prompt 段 1 该图描述 + 段 3 该段旁白-动作对应 + 末尾约束**三处**都显式声明「标题文字固定为参考图的 X，旁白词 Y 不得出现在画面文字中」。若仍污染，回退到陷阱 #2 方案（generate_audio 只用于音效，旁白用 MiniMax TTS 独立生成，从源头消除音频文本解析机制）。

> ⚠️ **2026-08-18 巧克力 Chocolate 实测 · 三处声明仍可能失败，直接回退陷阱 #2**：巧克力绘本 prompt 已按上面三处声明写全（段1 逐图「此图标题文字固定为 chocolate/巧克力，不得改动」+ 段3「旁白词不得出现在画面文字中」+ 末尾「禁止大小写互相变形；旁白词不得出现在画面文字中」），但图7 段「巧克力淋在蛋糕上」的中文标题仍被旁白词**整行覆盖**成「淋在蛋糕上」（英文 chocolate 保留、中文被换）。**结论：三处声明对「旁白中文词覆盖标题」机制不是可靠修复**——同一 clip 里图1/3/8 对、图7 错，逐图独立。若重做后仍有个别图中文被旁白词覆盖，**不要再反复重提烧钱**，直接回退陷阱 #2（generate_audio 只用于音效，旁白用 MiniMax TTS 独立生成），从源头消除音频文本解析机制。Step 7 必须**逐图**核对标题文字（英文+中文都要查），不能抽查一张就下结论。

Seedance 默认把参考图当"视觉风格参考"而非"画面元素保留"。如果不显式要求保留文字，模型会自由发挥。单靠段1一句"保留文字"不够——需要在 prompt 的**3 个位置**分别声明。

### 修复方案（3 位置强制声明）

**位置 1 · 段 1 主体+视觉基底** — 描述参考图时写：
```
保留参考图中的"RICKSHAW"和"人力车"文字作为画面元素
```

**位置 2 · 段 2 每个镜头描述末尾** — 每个镜头末尾加：
```
保留参考图中的"RICKSHAW"和"人力车"文字在画面上方
```

**位置 3 · 末尾约束** — 末尾约束改为：
```
保留参考图中的"RICKSHAW"和"人力车"文字作为画面元素，无水印、无背景音乐
```

### 完整示例

```markdown
段1 · 主体+视觉基底：
@Image1 红色人力车停在石板路上，车头朝右，有红色篷顶和两个大轮子，
上方有"RICKSHAW"和"人力车"彩色文字，背景浅蓝色天空。
保留参考图中的"RICKSHAW"和"人力车"文字作为画面元素。

段2 · 主体动作序列（按事件分镜）：
镜头1（@Image1 + 段1旁白）：镜头从远处缓缓推近，红色人力车从画面远处驶入画面中央，
保留参考图中的"RICKSHAW"和"人力车"彩色文字在画面上方。

末尾约束：保留参考图中的"RICKSHAW"和"人力车"文字作为画面元素，无水印、无背景音乐
```

### 注意事项

- 文字内容必须跟参考图**完全一致**（大小写、标点、中英文顺序）
- 文字位置描述用"画面上方/画面中央/画面顶部"等方向词，不要用精确坐标
- 如果多张参考图文字位置不同，每张图分别描述
- 3 位置声明是**强制**的，只写末尾约束不够（2026-08-04 实测结论）

> ⚠️ **2026-08-16 白鲸实测 · 多图 Clip 大小写必须逐图精确保留**：同一 clip 里不同参考图的标题**大小写可能不同**（白鲸图1=`BELUGA` 大写、图2-4=`beluga` 小写；气垫船图1=`HOVERCRAFT` 大写、图2-9=`hovercraft` 小写）。Agent 曾把所有图统一改成小写 `beluga` → 用户反馈「文字与参考图不一致」。**修正：每张图按其参考图实际大小写单独写**，prompt 段 1 逐图写「图N 顶部有彩色「BELUGA/白鲸」」，末尾约束列全所有变体（`保留参考图中的「BELUGA/白鲸」和「beluga/白鲸」文字`）。注意：大小写只影响**画面装饰文字**（段1+末尾约束），不影响段 5 旁白/音频（旁白文本保持 SRT 原样用于发音）。

> ⚠️ **2026-08-19 冰淇淋实测 · seedance 自行降格全大写标题首字母**：参考图标题全大写 `ICE CREAM`，prompt 段1+末尾约束都正确写了 `ICE CREAM`（未写成小写），但 seedance 仍把首字母降成小写，渲染成 **`iCE CREAM`** → 用户「文字与参考图不一致」。这是**模型自身的大小写不稳定**，区别于上面白鲸案例（agent 写错大小写）。**排查**：Step 7 抽帧后要特别问视觉模型「首字母是大小写？」（不能只确认英文/中文都在），全大写标题最容易首字母被降格。**处理**：这类首字母降格若用户不接受，与旁白词污染同理——重做上限 1 次，仍降格就回退陷阱 #2（generate_audio 只用于音效、旁白 MiniMax 独立生成），或接受后在剪映用文字覆盖修正。

> ⚠️ **2026-08-19 汤绘本实测 · 标题「混合大小写」也是合法变体，必须逐图精确保留**：汤绘本 8 张图出现 **3 种大小写变体**——图1/图8 `SOUP`(全大写)、图2/4-7 `soup`(全小写)、图3 `Soup`(**首字母大写 + oup 小写的 title-case 混合**)。**不能把 title-case 当成「笔误」统一降成小写或升成大写**——`Soup` 是参考图的实际样式，必须原样保留。**做法**：段1 逐图按其参考图实际大小写写（图3 写 `"Soup"`），末尾约束列全所有变体（`保留参考图中的"SOUP/soup/Soup"`）；Step 7 抽帧后**逐图单独问该图英文大小写**（对 title-case 图要特别问「首字母是否大写 S、其余是否小写」），不能只抽查一张就下结论。此案例把大小写逐图保留从「2 类（大写/小写）」扩展为「3 类（大写/小写/混合）」。

> ⚠️ **2026-08-31 工程师批实测 · 文字保留失效又添两个更彻底变体：整片消失 + 逐格拼写动画（方格识字卡/贴纸字样式高发）**：参考图原有两行核心词（engineer/工程师），即使段 1+硬性约束都写了「从第一帧到最后一帧一直显示、绝不消失」，仍出现：① **整片消失**——clip6 v2 全片画面无任何核心词文字（胸前/底带/顶带三处放大取证全查无），原有「绝不消失、绝不淡出」约束压不住；② **逐格拼写动画**——clip5 v2 把方格识字卡自作主张做成「字母逐格浮现」（f0 只有 1 格、f1 拼 5 格、f2 起才完整 8 字母）→ 早帧核心词不完整 = 铁律违规，且只抽查中后帧会漏判。**有效修法（round3 一次过验证）**：段 1 文字段追加「**文字出现方式铁律**：这两行文字从第一帧起就完整显示在画面中并保持到最后，绝不逐字浮现、绝不逐格拼写、绝不出现只有部分字母或空方格的状态、绝无空格子与占位方块，字母绝不逐个进场」；贴纸字场景再加「第一帧起就完整存在，若是首帧缺失则整镜头不合格」。**验收**：抽帧必须含 f0 极早帧（t<0.1s），专查文字是否完整在场（空格子/部分字母=不过）。

### 旧方案（保留作为备选）

如果 3 位置声明仍无效，回退到旧方案——在末尾约束中显式禁止文字创作：

```markdown
保留参考图中的「暴风雨」「STORM」「storm」文字作为画面装饰元素不变，
禁止自行创作或替换任何中文文字内容。无水印、无背景音乐。
```

注意：旧方案是**补充性**的，不能替代 3 位置声明。两个修复必须同时做。

## 陷阱 #5：横版参考图直接喂 9:16 竖版（2026-08-04 Garbage Truck 实测 · 2026-08-16 骆驼实测修正）

> **⚠️ 2026-08-16 修正（骆驼实测推翻旧结论）**：旧版本陷阱说「直接喂原始横版 + ratio=9:16 让 AI 自行处理构图」即可。**骆驼实测推翻了这个结论**：当横版与竖版比例差异过大时（1920x1200 = 3:2/1.6 → 9:16/0.56），直接喂横版会让 Seedance 硬拉变形、构图怪异、画面被粗暴裁切。用户明确反馈「画面不好看」。旧结论只在比例接近（如 16:9 → 4:3）时勉强成立，**跨大比例差异（横→竖）必须走下面的优先级**。

### 问题

用户提供的参考图是横版（1920x1200，16:9 或 3:2），但要求生成竖版（9:16）视频。Agent 先给图片上下加黑边补成 9:16 再喂 seedance，用户反馈"画面不好"。

### 根因

- 加黑边方案：上下大片黑边破坏画面美感，seedance 图生图时黑边区域被当作"画面内容"处理，产生奇怪效果
- 直接喂原始横版图 + ratio=9:16（旧结论）：**跨大比例差异时会硬拉变形/粗暴裁切**——seedance 是"图生视频"不是"修图"，跨比例硬转必翻车。数值参考：3:2 横版中央裁出 9:16 只保留 **35%** 画面、丢掉 **65%** 水平内容。

### 修复方案（按优先级排序 · 联网调研业界共识）

1. **首选：让用户重新提供竖版（9:16 或 3:4）参考图**。唯一保证美感的方法。在生图阶段（Seedream/即梦"图生图 + 指定比例"）就产出竖版，不要在视频阶段硬转。
2. **次选：先"竖版扩图"再喂视频**。用 Seedream/即梦的"画布扩图"把横版补成竖版（AI 补背景），得到竖版参考图后再喂 seedance。**关键：扩图在"生图模型"做，不在"视频模型"做**——生图模型补背景质量高，视频模型硬拉会变形。
3. **最次：中央裁切**。仅当确认主体就在画面中央、丢掉两侧不影响时可用。对全身/大场景构图（如骆驼+沙漠）裁切必毁。

> ⚠️ **反模式（已废弃）**：`直接喂原始横版图 + ratio=9:16 让 AI 自行处理` —— 骆驼实测已推翻，跨大比例差异时是错的。

> **⚠️ 2026-08-19 冰淇淋实测 · 用户坚持直接喂横版 9:16 时出现"上下黑边"（信箱模式）的修复措辞**：3:2 横版参考图直接喂 9:16，seedance 可能把横版内容塞进竖屏容器、上下留大片黑边（clip2 实测，与同批其它填满竖屏的 clip 明显不一致 → 用户"竖版不美观，与其它视频不一致"）。**成功修复措辞（段1 每张图 + 段2 每个镜头 + 末尾约束三处都写）**：
```
画面严格固定为9:16竖屏，{主体}放大居中充满整个竖屏，背景{底色}填满全画面，上下左右均无黑色或空白边缘
```
三处声明缺一不可；段2 每个镜头也要带"画面充满整个竖屏，上下左右无黑色边缘或空白区域"。重做后抽帧 vision 复核黑边是否消除（看上下边缘是否纯黑）。**与陷阱 #9 竖版留白区分**——#9 是主体太小在近景/中景下留白，这个是横版参考图被信箱化加黑边；#9 用"近景填满"，这个用"放大居中充满竖屏+背景填满"。

> **⚠️ 2026-08-19 馒头绘本实测 · 竖屏强制句 = 黑边反模式（与上面"放大居中充满竖屏"措辞相反）**：prompt 段1 写「画面严格固定为9:16竖屏比例。将参考图放大并裁剪，使主体充满整个画面，上下左右均不留任何空白区域」→ seedance 反而保留横版构图嵌进竖屏、上下留大片黑边（信箱模式），跟同批其它填满竖屏的 clip 明显不一致，用户「竖版不美观，与其它视频不一致」。**根因**：这句"放大裁剪"让 seedance 把横版内容当整体塞进竖屏容器，而不是重新构图。**正确做法（火锅流程）**：**不写任何竖屏强制句**，直接喂横版参考图 + `ratio=9:16`，seedance 原生输出 720x1280 满屏竖版。**判断**：若同批其它 clip 都自动填满、唯独某 clip 黑边，先检查该 clip prompt 是否误加了"放大裁剪/固定为9:16"这类强制句——去掉重提，比 ffmpeg 后处理更干净。ffmpeg 后处理（cropdetect+scale）仍是文字已正确、仅画幅不美观时的最后手段。

> **⚠️ 2026-08-19 爆米花实测 · 竖版黑边重提多次仍失败时，用 ffmpeg 后处理裁边填满（不再烧钱重提）**：clip1 横版图被信箱化上下各留 ~340px 黑边，prompt 写"放大裁剪充满竖屏"重做 1 次仍黑边。此时**停止重提 seedance**，改用 ffmpeg 后处理：`cropdetect` 找内容区 → `crop`+`scale` 放大填满竖屏，省 token 且效果与同批填满竖屏的 clip 一致（冰淇淋 clip2 那次是侥幸重提成功，爆米花这次确认了不可靠）。步骤：
```bash
# 1) 检测内容区（去掉黑边）
ffmpeg -i in.mp4 -vf "cropdetect=24:16:0" -frames:v 50 -f null - 2>&1 | grep -o 'crop=[0-9:]*'
# 输出如 720:624:0:340 = 内容 720x624、上下各 340px 黑边
# 2) 裁掉黑边 + 放大填满 9:16
ffmpeg -i in.mp4 -vf "crop=720:624:0:340,scale=720:1280:force_original_aspect_ratio=increase,crop=720:1280" \
  -c:v libx264 -crf 20 -c:a copy -movflags +faststart out.mp4
# 3) 抽帧 vision 复核：黑边消除 + 标题完整未被裁掉（放大可能裁切到上下标题，务必查）
```
⚠️ 注意：放大裁剪可能裁到标题文字或主体边缘，抽帧 vision 复核"两行标题完整可见 + 主体没被切关键部位"。这是文字已正确、仅竖版不美观时的**最后手段**——先确认文字 OK 再用它修画幅，别跟文字修复混在一次重提里。

## 陷阱 #6：Seedance 内置 TTS 旁白内容念错（2026-08-04 Monorail 实测）

### 问题

Seedance generate_audio 有时会念错旁白内容，特别是当句子包含颜色+物体+英文混合时：
- 旁白原文：`"红色的单轨列车，monorail"`
- Seedance 念成：`"红色单轨的货车"`

### 根因

Seedance 内置 TTS 对中文长句的语义理解不稳定，容易混淆同类物体（如"单轨列车"→"货车"）。

### 修复方法

在段 5 音频描述的人声旁白行后加括号注释，显式纠正：

```markdown
段5 · 音频描述：
人声旁白："红色的单轨列车，monorail"（注意：旁白是"红色的单轨列车，monorail"，不是货车，是单轨列车）
音效：列车行驶声
```

### 原理

Seedance 的 TTS 模型会读取括号内的纠正说明作为额外上下文，提高旁白准确率。

### 如果一次修复不成功

- 加强注释措辞（更明确地指出错误内容）
- 重新提交同一 prompt（seedance 每次生成有随机性）
- 如果多次失败，回退到陷阱 #2 方案（generate_audio=true 只用于音效，旁白用 MiniMax TTS 独立生成）

### 反模式

- ❌ 只改 prompt 段 1-4 不改段 5 音频描述
- ❌ 重新提交完全相同的 prompt（不解决问题）
- ✅ 在段 5 加括号纠正注释后重新提交

## 陷阱 #7：核心词文字拆成两组独立元素（2026-08-06 热气球实测）

### 问题

prompt 段 1 把核心词拆成两组独立文字元素描述：
```markdown
❌ 错误：
画面上方有彩色「hot air balloon」字母和「热气球」中文装饰文字。
```
→ Seedance 把英文和中文当作两组独立文字渲染到画面 → 画面出现两组文字（英文+中文分开显示）

用户要求：**每张图只保留一组核心词**。

### 修复方案

```markdown
✅ 正确（一组核心词，斜杠连接）：
画面上方有彩色「hot air balloon/热气球」装饰文字。
```

### 根因

### 适用范围

所有包含文字元素的参考图 prompt 段 1 描述。不限于热气球，适用于高铁/缆车/马车/挖掘机等所有主题。

### 例外

如果参考图本身就有两组文字（如 1.jpg 有「HOT AIR BALLOON」大写 + 2.jpg 有「热气球」中文），则每张图按参考图实际文字描述，但**同一张图内只写一组**。

## 陷阱 #8：Seedance TTS 英文发音不准确（2026-08-06 挖掘机实测）

### 问题

Seedance 内置 TTS 对多音节英文单词发音不准确，如 "excavator" 重音位置错误。

### 修复方案

在段 5 音频描述的人声旁白行中加 IPA 音标 + 重音标注：

```markdown
❌ 错误（无发音指导）：
人声旁白：「挖掘机 EXCAVATOR！」— 温柔女声，语速偏慢，领读节奏清晰，「EXCAVATOR」处语调上扬。

✅ 正确（IPA + 重音标注）：
人声旁白：「挖掘机 EXCAVATOR！」— 温柔女声，语速偏慢，领读节奏清晰，excavator 读作 /ɪkˈskeɪvətər/ 重音在第二个音节，「EXCAVATOR」处语调上扬。
```

### 适用范围

- 多音节英文单词（excavator, carriage, caterpillar, mechanical, hydraulic 等）
- 拼写不规则的英文单词
- 段 5 中每个出现该单词的人声旁白行都要加，不能只加第一处

> ⚠️ **2026-08-16 白鲸实测 · 单 IPA+重音不够，需加"音节拆分 + 常见错误重音"**：白鲸 beluga 用户反馈"发音不标准"，仅写 `/bəˈluːɡə/ 重音在第二个音节` 无效。**有效的加强写法**：① IPA 音标 ② 拆分音节并标重音大写 `/bəˈluːɡə/ 重音在第二个音节 lu，读作 buh-LOO-guh（不-路-嘎）` ③ **点出常见错误** `注意「beluga」不是 be-lu-GA、重音不在最后一个音节` ④ 元音要求 `元音发标准，不要拖长或吞音`。段 5 中每个出现处都要带全这套注释。教训：Seedance 内置 TTS 对多音节词常把重音放错音节，光给 IPA 不给音节拆分+错误对比，TTS 仍可能念错。

> ⚠️ **2026-08-31 牙医实测 · 同批兄弟词混淆（dancer→dentist）+ 1 次加强即修**：clip5 旁白「牙医看我的牙齿，dentist」被内置 TTS 念成 "Danced"——疑似同批/同书词汇 dancer 的近形迁移（模型把词库里学过的近形词带偏目标词）。基础写法（IPA /ˈdɛntɪst/ + 重音首音节 DEN + 音节拆分 DEN-tist）仍被念错。**有效加强 = 常见错误点名要含「词身 + 词尾」两层**：`注意常见错误：这个英文词是 dentist（登-提斯特），不是 dancer（丹瑟）也不是 Danced；第二个音节必须读 -tist（提斯特，t 清晰爆发收尾），绝不能读成 -cer 或 -ced 音`。加强后重提 1 次即修好（重做上限 1 次纪律不变）。判「真念错」还是 ASR 噪声：可疑 clip 用 faster-whisper 以 `beam_size=5/8` 双跑 + `word_timestamps=True` 看发音段起止——跨 beam 稳定输出同一错词 = 真念错；单次异常 = 先复测再决定，别直接烧钱重提。

## 陷阱 #10：Seedance TTS 中文发音不准确（2026-08-06 挖掘机实测）

### 问题

Seedance 内置 TTS 对中文多音节词发音不准确，如「挖掘机」的「机」被读成三声 jǐ 而非一声 jī。

### 修复方案

在段 5 音频描述的人声旁白行中加拼音 + 声调标注：

```markdown
❌ 错误（无发音指导）：
人声旁白：「挖掘机在挖土，excavator」— 温柔女声，「挖掘机在挖土」处语气带力量感。

✅ 正确（拼音 + 声调标注）：
人声旁白：「挖掘机在挖土，excavator」— 温柔女声，「挖掘机在挖土」处语气带力量感。中文「挖掘机」读作 wā jué jī（挖一声、掘二声、机一声），注意「机」是一声 jī 不是三声 jǐ，每个字清晰饱满。
```

### 关键要素

1. **拼音标注**：`wā jué jī` — 提供完整拼音
2. **声调标注**：`（挖一声、掘二声、机一声）` — 每个字的声调
3. **常见错误纠正**：`注意「机」是一声 jī 不是三声 jǐ` — 显式指出易错字
4. **每个出现处都加**：段 5 中每个出现该中文词的人声旁白行都要加，不能只加第一处

### 常见易错中文词

| 词 | 正确读音 | 常见错误 |
|---|---|---|
| 挖掘机 | wā jué jī（挖一声、掘二声、机一声） | 机读成三声 jǐ |
| 推土机 | tuī tǔ jī（推一声、土三声、机一声） | 机读成三声 jǐ |
| 缆车 | lǎn chē（缆三声、车一声） | — |
| 热气球 | rè qì qiú（热四声、气四声、球二声） | — |

> ⚠️ **2026-08-17 圆规实测 · 简单基础词也念错 + 不要反复烧钱重提**：旁白「圆规画大圆，也画小圆，compass」中的「大圆/小圆」是**极简单的双字词**（无多音节、无声调陷阱），但 Seedance 内置 TTS 连续 2 次重做仍念不准。教训：**① 不是只有多音节/易错词才念错，基础词也可能稳定念错；② 重做 1 次后仍错 = 别再反复重提烧钱**，直接交给用户剪映自有 TTS 覆盖（用户本来就偏好自然音频，不用 seedance 内置 TTS）。给用户贴出 clip 的完整旁白 + 时间点，方便剪映里对。

> ⚠️ **2026-08-31 工程师批实测 · 中文吞字/重复音节 + 中英滑音两种新念错形态（三 beam 判例法扩展到中文侧）**：① clip1「工程师」被内置 TTS 念成「**工程程师**」——beam 5/8/3 三跑稳定输出同一重复音节 = 真念错（跨 beam 稳定即判真，与牙医 dancer→dentist 同判例，扩展到中文吞字/加字）。修法 = 段 5 加「发音铁律（最高优先级）：『工程师』三字必须逐字清晰读作 gōng chéng shī（工一声、程二声、师一声），音节之间清晰断开，绝不能吞字、连读、加字或读成任何变体（特别禁止读成『工程程师』或其他重复音节）」→ round3 一次修好（beam5+8 复测干净）。② clip2「我看见工程师了，engineer」中「师了」与后随英文 engineer 粘连滑音，ASR 稳定转出「工程师尼爾了/工程师尼尔了/工程师neer了」——根因 = 中文尾字与英文词连读产生近似英文音节的效果；**ASR 转出繁体（工程師尼爾）也是可疑信号**。修法（round4 已提交，验收见后续）= 「绝对禁止把『师了』连读成任何近似英语音节的效果（特别禁止读成『尼尔』『neer』『neir了』等），中文与英文之间必须有明显停顿分隔」。**判例纪律**：中文侧可疑转写（同音字/繁体）复测时先给 `initial_prompt=简体旁白原文` 压噪声，但**错词跨 beam 仍稳定出现 = 真念错**，按重做上限 1 次纪律处理。

### 原理

Seedance 的 TTS 模型会读取拼音和声调标注作为发音参考，提高中文发音准确率。显式指出常见错误（"不是三声"）比只给拼音更有效。

## 陷阱 #11：横版参考图转竖版视频的画幅处理（2026-08-16 骆驼实测）

### 问题

用户给横版参考图（1920x1200，3:2），要求出 9:16 竖版。直接喂横版图 + `ratio=9:16` 让 Seedance 自己处理 → 画面不好/主体变形。

### 根因与数据

横版转竖版的损失是数学必然：
- `1920x1200`(3:2) 中央裁切成 9:16 → 保留区 `1200×0.5625 ≈ 675px` 宽
- **只保留原图 35%，丢弃 65% 水平画面**（骆驼身体/沙漠/天空被切一半）

### 处理优先级（唯一能保证美感的路）

1. **首选**：让用户重新提供竖版（9:16 或 3:4）参考图
2. **次选**：用 Seedream/即梦"画布扩图"先把横版补成竖版参考图，再喂 Seedance 做图生视频。**扩图在"生图模型"做，不在视频模型硬拉**——生图模型扩背景质量高，视频模型硬拉会变形
3. **最次**：中央裁切（仅当主体在画面中央、丢两侧不影响时）
4. ❌ **错误做法**：直接喂横版 + `ratio=9:16` 让 Seedance 自己处理（skill 旧方案）→ 硬拉/硬补导致主体变形

### 注意

- 若用户明确说"先不解决画幅，先调运镜看效果"，尊重用户决策，画幅问题单独立项

> **⚠️ 2026-08-20 公交车三次实测 · 推翻「中央裁切横版图」结论：对横向主体（公交/救护车）直接喂横版原图 + ratio=9:16 + 段1不写景别，才是唯一可靠且美观的解**：公交 8 张横图 1920x1200，我先后试了「全景平视居中偏下」「特写平视+放大充满」两种 prompt 措辞都仍留白/裁边，又试了「PIL 中央裁成 675x1200 再喂」→ **用户明确否定「图片裁剪过度导致视频中图片极其不美观」**（车头/车尾/车轮被切掉）。**最终正确解 = 直接喂横版原图 + ratio=9:16 + 段1不写景别**（直接"主体+特征+背景"），seedance 默认全景完整展示整车、上下用天空/草地/路面等装饰性内容自然填充，效果美观（救护车 4 个 clip 同模板一次过）。**教训：① 手动裁剪参考图 = 用户最反感（毁主体完整性）；② 对横向主体写景别（特写/近景）会让 seedance 放大裁切车头车尾；③ 不写景别让 seedance 自己决定全景构图最稳。**

### 视觉模型判断字母大小写：看字母形状而非颜色/整体（2026-08-20 公交/飞机实测）

彩色拼贴字母的大小写（BUS vs bus）视觉模型识别极不稳定——同一帧不同模型/不同轮次可能报大写、小写、title-case 各不相同。**最可靠 = 看字母形状**：
- **大写 B**：竖线 + **上下两个**封闭圆肚；**小写 b**：竖线 + **右下一个**圆肚。
- 大写 S/U 高度占满字高；小写 s/u 不占满、有下降部。
用放大裁剪图（`crop=720:330:0:0,scale=1440:660`）或直连 kimi OCR，按字母形状逐字判断，别凭整词「看起来像大写/小写」下结论。**铁律：视觉模型报大小写异常时，先怀疑是模型误读（尤其彩色拼贴字），对照已知参考图自检，别凭单次 vision 结论烧钱重做（参考「自检视觉模型」段）。**

## 陷阱 #12：竖屏裁切场景禁用推拉镜头（2026-08-16 骆驼实测）

### 问题

竖屏裁切后使用推近/拉远镜头，画面"看着不舒服、没美感、一会近一会远"。

### 根因

- 旧 skill 模板"全景开始→推近到 80%→拉远回全景"是机械模板，每镜头都推了又拉 = 无叙事节奏
- 竖屏裁切过的画面再做推拉，视觉上很不舒服（用户原话"要特别谨慎，尽量不要用"）

### 修复方案

- 每镜头只做一个运镜，**不做"推了又拉"**
- 运镜要有"起承转合"叙事节奏，不是每镜都动：
  - 镜头1（开场）：`固定全景`建立
  - 镜头2（推进）：`横移`扫过主体
  - 镜头3（高潮）：`固定`特写 / 主体动作强调
  - 镜头4（收尾）：`固定全景`呼应开场
- 推荐组合：**固定 → 横移 → 固定 → 固定**（零推拉）
- `跟拍`只在主体本身水平位移时用，否则空转
- 禁用运镜词：`推近`、`拉远`、`推进`、`由远及近`、`由近及远`

## 陷阱 #14：批量生产时 verify_prompt 的两个高频 FAIL（2026-08-16 海龟/海星/鱿鱼/珊瑚/白鲸 5 本实测）

> **定位**：多 Clip 批量生产（一次 5 本 × 各 3-4 Clip）时，`verify_prompt.py` 几乎每本都会踩到以下两个 FAIL。它们是**确定性修复**，写 prompt 时主动避开即可，不用等验证报错再改。

### FAIL 1：R3 凝固语命中 `保持.*?稳定`（防跳跃措辞的坑）

按陷阱 #13 写"防身体部位跳跃"时，**不能写"保持稳定"**：
```
❌ 身体主体保持稳定不动   → R3 正则 `保持.*?稳定` 命中 → FAIL
✅ 身体主体稳定不动       → 去掉"保持"二字 → 通过
```
本 skill 所有"防跳跃/防变形"措辞统一写成 `X 稳定不动不晃动`（海龟实测 3 个 clip 全中招）。

> ⚠️ **2026-08-19 冰淇淋实测 · R3 跨句假阳性（"保持"与"稳定"在不同分句仍 FAIL）**：R3 正则 `保持.*?稳定` 里的 `.` 会匹配**句号/换行**，所以 `画面严格保持9:16竖屏比例，画面填满…蛋筒格纹稳定不动不晃动` 会命中 FAIL——"保持"(竖屏比例) 和 "稳定"(蛋筒格纹) 在完全无关的分句里。**修法：画幅/比例/尺寸类表述不用"保持"，改用"固定为"**：`画面严格固定为9:16竖屏比例`（"固定为"不触发 `保持.*?稳定`）。**排查技巧**：`grep "保持.{0,6}稳定"` 无结果但 verify 仍报 R3 时，用 `grep -noE "保持.{0,30}稳定"` 扩大跨度，找"保持"与"稳定"相距较远的跨句位置。

### FAIL 2：R11 缺空间目标（固定镜头的坑）

固定镜头没有位移，verify_prompt R11 会报"缺空间目标"。**固定镜头不是不加位置词**，而是补位置描述：
```
❌ 固定镜头，海星趴于岩石中央   → R11 FAIL（无 R11 白名单关键词）
✅ 固定镜头，海星趴于画面中央的岩石堆上  → "画面中央"命中 → 通过
```
固定镜头统一写 `立于/趴在/居于 画面中央`（或 `画面中央偏下`），一次补到位。海龟/海星/白鲸实测均踩过。

### 批量生产速查

- 每本写完所有 Clip 的 prompt 后，**统一跑一轮 `verify_prompt.py`**，把这两个 FAIL 一次性修完，再进 Step 6 提交
- 修复口诀：身体部位用 `稳定不动`、固定镜头用 `画面中央`，二者都是"零推拉 + 防跳跃"方法论的配套写法

### FAIL 3：R10 缺「人声旁白」= 走 MiniMax 旁白路线时的**已知预期 FAIL，直接忽略**（2026-08-19 粥实测）

按陷阱 #2（generate_audio 只用于音效、旁白用 MiniMax TTS 独立生成）写段 5 时，`verify_prompt.py` 的 **R10 必然报 FAIL**：`路径 A(有 SRT) 但 prompt 缺 '人声旁白：'`。**这是规则冲突，不是写错**——R10 硬要求 `人声旁白:"{SRT原文}"`，但陷阱 #2 明确禁止写人声旁白原文（写了会被 seedance 渲染成画面标题污染，见陷阱 #1）。

**处理**：只要确认段 5 只写 `音效:{...}` 且走 MiniMax 旁白路线，**R10 FAIL 直接忽略，不修**。只修 R11（和真实 R 规则）等其它 FAIL，让 prompt 保持"段 3 只写英文核心词 + 段 5 只写音效"的正确结构。**不要**为了让 verify 变 ok 而强行补 `人声旁白:` 行——那会引入污染源。判断标准：`"ok": false` 里只剩 R10 一条 = 可以提交；还夹着 R11 = 先修 R11。

### FAIL 4：R11 推近镜头写"到 X 特写"不满足空间目标正则，必须写"在画面中央…特写"（2026-08-19 粥实测）

推近/推进镜头想满足 R11 空间目标时，**"到 X 特写" 这种终点式短语不匹配**（space_regex 里没有"特写"作为终点词）：

```markdown
❌ 镜头从全景缓慢推近到白粥碗特写     → R11 缺空间目标 FAIL
✅ 镜头从全景缓慢推近，白粥碗在画面中央逐渐放大到特写   → 命中"画面中央" → 通过
```

推近镜头统一写 `镜头从全景缓慢推近，{主体}在画面中央逐渐放大到特写`（「画面中央」一次补到位），与固定镜头用「画面中央」是同一套路（见 FAIL 2）。

### FAIL 5：段 2 镜头标签擅自改词 → R9/R28 双双 FAIL（2026-08-20 飞机实测）

写段 2 动作序列时**不要擅自把「镜头 N」改成「画面 N」**（想避开跟末尾约束里「画面」一词重复的动机）——verify_prompt 的正则依赖**字面 `镜头 N:`** 标记做多镜头计数（R28）和收尾定位（R9 找 `镜头 N 末尾`）。改成语义等价但字面不同的词，R28「找到 0 个镜头标记」+ R9「段 4 缺收尾位置标记」会一起 FAIL：

```markdown
❌ 段2 写「画面 1（…）：」→ R28 找不到 '镜头 N:' → FAIL；段4 写「画面 3 末尾」→ R9 找不到 '镜头 N 末尾' → FAIL

## 陷阱 #11：运镜机械模板化（每个镜头都"推近又拉远"）（2026-08-16 骆驼实测）

### 问题

用户强烈反馈运镜"非常垃圾"、"一会近一会远的运镜方式，根本没有运镜的美感，也没有叙事的表达"。根因是 prompt 把**每个镜头**都写成同一套机械模板：`全景开始 → 推近到 80% → 拉远回全景`。一个 clip 里 4 个镜头全这样，等于每个镜头都在做相同的推-拉，毫无叙事节奏，画面像来回缩放。

### 根因

"每个镜头都推又拉"是把**运镜当作填充动作**，而不是为叙事服务。运镜要有"起承转合"的节奏差，不能逐镜重复。

### 修复方案（一镜一运镜 + 叙事节奏）

**每个镜头只做一种运镜，且整组镜头用不同的运镜构成起承转合：**

```
❌ 反模式（每个镜头都推近又拉远，机械重复）：
镜头1：全景开始→推近80%→拉远回全景
镜头2：全景开始→推近80%→拉远回全景
镜头3：全景开始→推近80%→拉远回全景
镜头4：全景开始→推近80%→拉远回全景
→ 每个镜头都在做相同的推-拉，毫无叙事

✅ 正模式（一镜一运镜，起承转合）：
镜头1（开场）：固定全景建立，先看清主体全貌，不做推拉
镜头2（推进）：运镜横移 / 跟拍，跟着主体动作走
镜头3（高潮）：缓慢推近，强调核心特征
镜头4（收尾）：缓慢拉远，呼应开场全景
→ 固定→横移→推近→拉远，节奏有变化、有叙事
```

### 关键原则（联网调研 Seedance 官方指南 + 专业案例共识）

1. **"每段时间只做一个运镜"** —— 一个镜头只做一种运动（推/拉/摇/移/跟/固定），**不要一个镜头里推了又拉**。多个专业案例反复强调（2000+ 提示词合集里的获奖案例明确写 "exactly one camera move per time slice"）。
2. **运镜要为动作服务，不是空转** —— 骆驼走→镜头横移跟拍；骆驼抬头→镜头推到头部。镜头自己推拉而主体原地，就是"垃圾运镜"。
3. **固定镜头是合法选择** —— 不是每个镜头都必须运镜。固定全景建立/展示环境/呈现互动（如两只动物亲昵）都合适，且能跟运动镜头形成节奏对比。
4. **运镜节奏模板**（多镜头 clip）：固定/广角建立 → 横移或跟拍 → 推近强调 → 拉远收尾。

### 注意事项

- 固定镜头也要写"画面中央/中央偏下"等位置词，否则会被 verify_prompt.py R11 拦成"缺空间目标"（固定镜头不算位移）。
- 这个反模式独立于"主体原地动"（RP-26a），两者可同时存在：既不能每镜都推拉，也不能主体原地。

---

生成后检查视频帧中是否出现：
1. 旁白原文被渲染为彩色文字（如"暴风雨 STORM！""夏至 SUMMER SOLSTICE！"等）
2. 参考图中不存在的文字内容
3. 参考图原有文字被替换为其他内容

如果出现上述任一问题，说明 prompt 中仍有旁白原文被 Seedance 读取为画面元素，或文字保留指令不够强。

## 陷阱 #16：视觉模型误读绘本文字 → 假阳性重做烧钱（2026-08-18 汉堡实测）

### 问题

Step 7 用辅助视觉模型（当时 `qwen3.5:397b`）逐图核对标题文字，**反复误读**，把正常画面判成"文字污染/缺中文"，导致我重做 clip 烧钱，最后用户目测说"没有问题"。

汉堡图4 实测：视觉模型连续 4 次重做都报"中文'汉堡'没保留/只有一行英文/出现'芝士'"——但用户目测 Clip1 完全正常。**根因是视觉模型对绘本小字/被遮挡文字识别不可靠，不是画面真有问题。**

### 修复方案

1. **重做前先怀疑视觉读数**：视觉模型报"文字污染/缺中文"时，先交叉验证（换帧/换时间点/看用户反馈），**不要凭单次 vision 读数就重做烧钱**。
2. **用户目测是最高权威**：用户说"我目测了没问题"→ 立即停止重做，接受当前 clip。用户的眼睛 > 视觉模型读数。
3. **视觉模型可配置**：`auxiliary.vision.model` 在 `~/.hermes/config.yaml`（用 `hermes config set auxiliary.vision.model <name>` 改，config 文件受保护不能直接 patch）。2026-08-18 已从 `qwen3.5:397b` 换成 `kimi-k2.7-code`（同一 ollama 提供商，`curl https://ollama.com/v1/models` 可查清单）。注意：改配置后**新开会话才生效**。
4. **重做上限纪律不变**：即便视觉读数可信，逐图文字污染重做上限 = 1 次，超限回退陷阱 #2。但**先确认读数不是误读**再决定是否重做。

### 反模式

- ❌ 视觉模型报"缺中文/文字污染"就立刻重做 → 可能是误读，白烧钱
- ❌ 用户说"没问题"后仍坚持重做 → 用户眼睛是最高权威
- ❌ 直接 patch config.yaml 改视觉模型 → 文件受保护，必须用 `hermes config set`

---

### 自检视觉模型 = 排除"模型是否正确"争议的最快手段（2026-08-20 飞机实测）

用户多次反馈文字不对、连续重做仍错，发飙「你自己检查一下所有的模型是否正确」——**核心动作是先把视觉模型自身可靠性钉死，再谈画面问题**。做法：

1. **拿已知答案的参考图测视觉模型**：用当前视觉模型直接 OCR 参考图本身（其文字内容是确定的，如飞机绘本 `1.jpg=AIRPLANE` 全大写、`2.jpg=airplane` 全小写、每张只有一行英文+一行中文）。若模型能逐字读对 + 大小写 + 单行，证明**模型可靠**，之前的报错是真实画面问题，不是误读。
2. **别用辅助视觉工具的 vision_analyze 反复问同一批问题帧**——用 `execute_code` 直接 POST 视觉模型 API（ollama `https://ollama.com/v1/chat/completions`，base64 data URL），一次批量 OCR 多帧，prompt 明确「逐字报大小写 + 数英文有几行 + 是否叠放 + 有无杂字」，比逐张 vision_analyze 快且结果可对比。
3. **放大裁剪顶部文字区再 OCR**（`ffmpeg -vf "crop=720:330:0:0,scale=1440:660"`）——彩色拼贴字母/小字在整帧里视觉模型易过度敏感，放大后能区分「真叠放」vs「字母错落排版」。
4. 确认视觉模型可靠后，剩余错报 = seedance 真问题，按对应陷阱修；确认模型本身误读 = 不重做，接受当前 clip。

**铁律**：用户质疑模型是否正确时，不要空口辩解，先用「已知答案参考图自检」证明给用户看（本次即用 1.jpg/2.jpg 已知大写/小写验证了模型可靠）。

## 陷阱 #20：起幅构图越界——写死半身仍在 f0 补全身/露腿脚（2026-08-31 工程师批实测）

### 问题

prompt 已写「半身构图铁律+绝不画出膝盖小腿裤腿鞋子+绝不补全身」（甚至首中尾三次强调），生成视频**起幅（第一二帧）仍越界**：clip1 v1/v2 的 f0 起幅全身双脚落地（中末帧才归位半身）；clip5 v2 f0 双腿至鞋头入画；clip2 行走场景 v2 f0 到裤腿、v3 f0 到鞋。越界集中在极早帧，中后帧多数正常。

### 根因
1. **「第一帧之后」措辞反噬**：prompt 写「双脚鞋子绝不出现在**第一帧之后**的任何一帧」= 字面上**隐式授权第一帧可以有脚**，模型按字面执行。
2. **开场镜头语言留想象空间**：未写死第一帧构图时，模型倾向「人物从远处走入→先全身后推近」的开场。
3. **截止部位模糊**：只写「半身至大腿中段」不够，模型对「到哪裁」自行加戏（clip2 v3 到鞋 vs 参考图实际截止大腿上部）。

### 修复模板（round3 clip1/clip5 一次过验证）

段 1 构图铁律后追加两句：
```
第一帧即为此半身构图并以固定取景开画：无入场走位、无走入画面、无镜头推拉，人物上半身从第一帧起就充满画面、裁切位置与参考图完全一致。
任何一帧都不出现裤腿、鞋子、双脚（含第一帧）。
```
关键变化：「含第一帧」显式取代「第一帧之后」；「无入场走位/无走入画面」封死开场全身入场。

### 行走/律动类 clip 的升级版（round3 失败 → round4 写死 ground truth）

**行走摆臂场景（clip2）round3 加了第一帧锁定仍越界到鞋**——「行走」的运动语义诱导模型补腿。round4 升级 = 先放大参考图取 ground truth（确认参考图实际画到哪个部位截止、有无裤腿/鞋），再在段 1 精确写死：`@Image2 半身至大腿上部截止：参考图中腰带以下只有极短一截裤料，绝无成型裤腿、绝无膝盖、绝无小腿、绝无鞋，本视频必须 1:1 复刻该截止线`，每处负面枚举都带「含第一帧」。

### 验收纪律
- 抽帧序列必须含 **t<0.1s 极早帧**（f0）——只抽 1.2s 起的五帧会漏掉起幅越界。
- **构图裁决必须先对参考图做 ground truth 取证**（放大参考图下半部，确认「参考图到底画到哪个部位截止」），再判生成是否多画部位；不能只凭 vision 对生成帧的「半身/全身」定性词下结论。
- 「脚在底边被裁切 + 画面内无悬浮」**不能豁免构图越界**——参考图没画到的部位，生成多画了就是越界（与参考图构图锁定的定义一致）。
- ASR（beam 5/8）与构图视觉复查互相独立，都要跑；vision 因配额中断时先跑完 freeze/ffprobe/ASR 等不依赖 vision 的硬-check，视觉分批小步走（一次 1-2 张、失败 sleep 45s 再试）。

## 音频/成片验收口径（批次一条龙 · 2026-08-31 牙医批沉淀）

> 配合舞蹈家批（/tmp/pb_video2）同款一条龙：8 clip 1图1段 → 20s 间隔轮询（≤10min）落盘 clipN.mp4 → concat（无 tpad/截断/转场/BGM，crf18 24fps）→ 自检三件套 → 回传。clip 时长 = `ceil(段 SRT span 含尾停顿)` 归到 [4,15] 整数；~30s 的 8 段 SRT → {4,4,4,4,5,4,5,5}=35s 已两次验证（舞蹈家/牙医）。提交走 build_body 直调（uguu files[] + 无 resolution/service_tier/watermark，见陷阱 #17 模板）。
>
> **ASR 旁白验收（faster-whisper small 逐 clip）**：硬指标 = **英文核心词精确匹配**（dentist/dancer…）；中文只验关键词出现——同音字/异体字（芽衣/牙衣、属/数、新型/新、親切/亲切）= whisper 归一化噪声，不算错，判错只看英文词。判念错流程见陷阱 #8 牙医注：beam 5/8 双跑稳定同一错词 = 真念错。faster-whisper 不在系统 python/hermes venv：**先复用历史批次的 `/tmp/pb_video/asr_venv/bin/python3`**（模型缓存 `/tmp/pb_audio/models`），被清了再装到该 venv（`pip install faster-whisper`，配 `HF_ENDPOINT=https://hf-mirror.com`），别装到系统环境。
>
> **venv 不在/跨机器时的第三条路（2026-08-31 牙医批二次实测 · A2A 状态速查）**：`UV_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple uv run --with faster-whisper python asr_*.py` —— 免建 venv，wheels 进 uv 缓存（24 包首跑 ~1min，二跑秒级）；**必须带清华镜像**，裸 `uv run` 走 pypi.org 直连超时（3×46s retry 起步，前台 terminal 420s 烧完才知白跑）。模型下载仍要在脚本 import faster_whisper 之前设 `HF_ENDPOINT=https://hf-mirror.com`。详见 `china-python-packaging` skill。
>
> **自检结论以当次实测为准（批会话 timeout 后的续查纪律）**：会话超时 = 自检根本没跑完；再被问「自检做了没」时，**脚本/venv 存在 ≠ 已跑完**，必须当次复跑 ASR（beam 5/8）+ ffprobe 时长才下结论，不能拿早前未完成会话的状态当通过依据。状态速查回答格式 = 逐条一行事实（文件数/存在性/大小/时长/结论/卡点），不叙述过程。
>
> **冻结验收（freezedetect，口径统一 d=2）**：全片 `ffmpeg -i final.mp4 -vf "freezedetect=n=0.003:d=2" -f null -` 计数 0 = 通过（舞蹈家批同口径）。**d=1 会把 seedance 原生片尾静场定格误报成冻结**：本批全片 34.67s 起 ~1.1s 静帧（clip8 末尾），d=1 报 1 个事件、d=2 报 0 个——这是模型尾帧行为，不要据此重做。分不清归属时对逐个 clip 单独跑 freezedetect 定位：单 clip 只有同款尾帧 = 正常；clip 中段报冻结 = 真问题（本批 clip5_v2 即此用法验证干净）。
